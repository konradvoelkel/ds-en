# How this edition is published, and what was wrong with it

Written 2026-10-14, after an external critique of the web edition was passed on. Every
claim below was checked against the **live site**, the built HTML and the CI
configuration — not against the source, and not against the critique's own reasoning.

The German original received the same critique and worked through it the same day; its
assessment is `todo/seo-kritik-bewertung.md` in ds-skript. This file is the English
edition's counterpart, and exists mostly to record the three things that differ here.

---

## 1. What the critique got wrong

**Its headline finding — that chapter URLs return 404 to crawlers — is false.** Measured:

```
/ds-en/            200        /ds-en/kmeans    301 -> /ds-en/kmeans/   200
/ds-en/robots.txt  200        /ds-en/sitemap.xml                       200
```

`myst build --html` writes `kmeans/index.html`; there is no SPA fallback, the body is
server-rendered (193 kB of text with JavaScript disabled), and Googlebot follows a 301
without complaint. The recommended fix — "run `myst build --html`" — is what the workflow
already did.

The critique was right that something was wrong with the sitemap. It guessed the cause
instead of fetching the file.

## 2. What was actually broken, and is now fixed

### The sitemap pointed at `localhost`. All 30 entries.

```
sitemap.xml:  <loc>http://localhost:3000/kmeans</loc>      ... 30 entries
robots.txt:   Sitemap: http://localhost:3000/sitemap.xml
```

MyST fetches `robots.txt` and `sitemap.xml` from its own dev server during the static
build and writes that server's origin into them. MyST 1.10 has no setting for the real
origin — `BASE_URL` sets only the path. So the site handed crawlers a sitemap in which
every URL pointed nowhere, and a `robots.txt` naming a machine that does not exist.

### No `rel="canonical"`, anywhere

MyST emits none. It matters here because the same text is also published as a PDF, and
because this edition is about to change host.

### `og:image` was relative *and* 267 x 50

```
<meta property="og:image" content="/ds-en/build/dd46c6ec….png"/>
```

OpenGraph requires an absolute URL — Slack, LinkedIn, Mastodon and WhatsApp cannot
resolve a root-relative one, so the preview card stayed empty.

**Beyond that, and this is the part neither critique nor the German assessment caught:
that image, `dd46c6ec….png`, is the Creative Commons BY-SA button — 267 x 50 pixels.**
MyST has no site-wide preview image; it takes the first image of a page, and where a page
has none it reaches for the first image of the project, which here is the licence badge
at the foot of the landing page. So 16 of 30 pages advertised the CC button as their
preview card. At 267 x 50 it is below the 200 x 200 minimum Facebook and LinkedIn
enforce, so making the URL absolute would have produced a rejected or hairline card
rather than a preview. Two further pages derived an SVG, which no platform renders as a
card at all, and one a 400 x 144 figure.

*(Corrected 2026-10-15. The first version of this file, and the German assessment, both
called that image "the site logo". It is not: the logo is `logo-wide-….svg` and was never
the fallback. The fix is unaffected, but the mechanism is worth stating correctly — it is
"first image on the page", not "the logo", which is why small figures broke it too.)*

**The German edition has the same fallback and the same problem; its `og:image` is now
absolute but still the 267 x 50 licence badge.** Passed upstream in `UPSTREAM-NOTES.md`.

### The fix

All of it is post-processing in `.github/workflows/pages.yml`, after the build and before
the artifact upload: rewrite the origin into `sitemap.xml` and `robots.txt`, give every
`<loc>` the trailing slash that actually answers 200, make `og:image` absolute, and add a
`rel="canonical"` plus `twitter:card` to each of the 30 pages. Nothing in the build or the
content is touched.

Plus a real preview card: `images/social-card.png`, 1200 x 630, generated by
`tools/social_card.py` and committed. `myst.yml` declares it as the project `thumbnail`,
so pages with a figure of their own keep theirs and the rest inherit the card; the four
pages whose derived image was unusable (an SVG, the logo, or 400 x 144) name it
explicitly in their frontmatter.

The deploy job now refuses to publish if a `localhost` URL survived, if the page count
and the canonical count and the sitemap entry count disagree, if any `<loc>` still points
at a redirecting URL, or if any `og:image` is still relative. The guards are written as
`if … then fail; fi`, not `check && fail` — a trailing `&& fail` makes the step fail
exactly when the check passes.

Both steps were extracted from the YAML and run against a copy of a real build before
being committed: 30 pages, 30 canonicals, 30 sitemap entries, all absolute.

## 3. The origin, and the move of 2026-10-15

`SITE_ORIGIN` and `BASE_URL` are one `env:` block at the top of `pages.yml`. Since
2026-10-15 they read:

```yaml
env:
  SITE_ORIGIN: https://datascience.konradvoelkel.com
  BASE_URL: ""          # custom domain serves from the root, not from /ds-en
```

The German edition deliberately stays where it is for now — HHU GitLab, HHU domain
(Konrad, 2026-10-15). Only this edition moved.

### Why GitHub Pages with a custom domain, and not the VPS

The obvious alternative was to serve the book from Konrad's own Hetzner box, next to the
other sites. It was rejected for this move, for three reasons:

1. **It would have needed a server key in GitHub secrets**, which `PLAYBOOK.md` §3.9
   records as a decision already taken and rejected ("CI-driven deploy of app or site was
   considered and rejected: it would put the keystore or a server key into GitHub
   secrets", LA DECISION §37). This repository has no secrets at all today, and that is
   worth keeping.
2. **GitHub redirects the old URLs for free, and with a real 301.** A tree of
   `<meta http-equiv="refresh">` stubs — the usual suggestion — is a soft redirect and
   strictly worse.
3. **The control argument is satisfied by owning the name, not the metal.** The domain is
   Konrad's, at INWX, in `~/files/work/server/dns/`. If GitHub ever becomes the wrong
   host, it is one DNS record and two lines in this workflow — which is exactly the move
   just performed, and it is now a rehearsed operation rather than a hypothesis.

The VPS remains available later; nothing in the build or the post-processing is specific
to GitHub Pages. Only the upload step would change.

### What was verified before the cutover

Built with `BASE_URL=""` and the deploy steps run against the artifact:

* 30 pages, 30 canonicals on `https://datascience.konradvoelkel.com/<slug>/`, 30 sitemap
  entries, `robots.txt` naming the right sitemap, every `og:image` absolute;
* JSON-LD present once, `url` and `image` on the new origin;
* `CNAME` written from `SITE_ORIGIN`, so it cannot drift from the canonicals;
* the artifact served from a local root and opened in a browser: assets, stylesheet,
  sidebar navigation and a chapter page all load with no `/ds-en` prefix anywhere.

**`CAA` was checked and permits this.** `konradvoelkel.com` carries
`0 issue "letsencrypt.org"` at the apex, which subdomains inherit; GitHub Pages issues
through Let's Encrypt, so the certificate can be provisioned. Had that record named a
different CA, the certificate would simply never have appeared — with no error anywhere
in the build.

### What must still be checked after the cutover

DNS and the repository setting are not things this repository can do. Once they are in
place:

```bash
curl -sI https://datascience.konradvoelkel.com/kmeans/ | head -1
curl -sI https://konradvoelkel.github.io/ds-en/kmeans/ | head -1   # expect 301
curl -s  https://datascience.konradvoelkel.com/robots.txt
```

The second line is the one to watch. GitHub redirects a project site's old
`username.github.io/<repo>/…` URLs to the custom domain once it is set, but **whether it
preserves the path after the repository name is worth confirming rather than assuming**.
If it redirects to `datascience.konradvoelkel.com/ds-en/kmeans/` instead of
`/kmeans/`, the fallback is to publish a small tree of redirect stubs from a second
workflow — worse than a 301, but correct.

The social card deliberately carries `konradvoelkel.com`, the author's own domain, rather
than the site URL: a URL baked into a PNG goes stale silently.

Still open, and no longer blocked by the move: the `hreflang` pair with the German
edition. It needs the German side to point back, which means a change in ds-skript's own
`pages` job; a one-sided `hreflang` is ignored.

## 3b. Accessibility findings from the second critique (2026-10-15)

Three claims about the rendered DOM, all checked:

* **The licence badge had no `alt`.** True, and it was our own raw HTML in
  `landing-page.md`. Fixed: it now reads "Creative Commons Attribution-ShareAlike 4.0
  licence badge". The German original has the same markup and the same gap.
* **The navbar logo had no `alt`.** True. The book theme has a `logo_alt` option; set in
  `myst.yml`. All 30 pages now carry zero images without an `alt` attribute (checked
  across the whole build, not just the landing page, which is where the critique looked).
* **The course diagram renders as an empty `<figure></figure>`.** True. MyST emits the
  mermaid source into the page's JSON payload and renders it in the browser; the static
  HTML holds an empty figure with no caption. *This one we cannot fix from the source:*
  the `mermaid` directive rejects a `:caption:` option (tested — "unexpected option
  caption"), and wrapping it in a `figure` directive would add a block and break
  alignment with the German original. The information itself is not lost to a crawler —
  the paragraph above the diagram and the table of contents below it carry the same
  structure in prose. Recorded in `UPSTREAM-NOTES.md` as a MyST limitation that affects
  both editions.

## 4. What the critique proposed that was already done

Chapter titles and per-chapter `description`s were the critique's points 3 and 4. Both had
already been inherited from the original in `68ce8b1` — 30 distinct descriptions, and
titles like `k-means: clustering, implemented from scratch` or `Numpy: vectorisation and
arrays`. The original deliberately **reformulated** the critique's suggested titles rather
than adopting them, because a chapter title is also the printed heading in a 328-page PDF
and the critique's phrasings are search strings, not chapter names. Four titles are still
thin (`Expected value and variance`, `Expectation maximization and Gaussian mixture
models`, `The most important discrete distributions`, `Introduction to Python`). The
second critique raised them again; **Konrad's decision of 2026-10-15 is to leave them.**

## 4b. Structured data (added 2026-10-15)

The second critique's one genuinely new and correct point: there was no JSON-LD. There is
now, on the landing page only — `tools/structured-data.json`, inserted into the built HTML
by `tools/inject_jsonld.py` from the deploy workflow.

Three decisions worth recording, because they depart from what was proposed:

* **`Book` + `LearningResource`, not `Course`.** The proposal declared `"@type":
  ["Book","Course","LearningResource"]` with `"provider": Heinrich Heine University
  Düsseldorf` and a `hasCourseInstance`. That would assert that this edition is a course
  offered by the university, which it is not — it is a translated book, and as of
  2026-10-14 deliberately not addressed to that curriculum at all (§6). Structured data
  is a claim made to search engines; a false one is worse than a missing one. The
  author's *affiliation* is a separate claim and a true one, so it stays.
* **Not in `landing-page.md`.** The proposal put the block in the page source via a
  `{raw} html` directive. That would be an extra block and would break alignment with the
  German original on the next `sync.py align`. It goes into the built HTML instead.
* **The card URL is read back out of the page**, not hardcoded: MyST fingerprints asset
  filenames, so the hash changes whenever `tools/social_card.py` regenerates the card.

The deploy job fails if the landing page does not end up with exactly one parseable
JSON-LD block whose `url` is this build's own origin and whose `image` is absolute —
stale structured data after a move is worse than none.

Verified on 2026-10-15 in both configurations: at
`https://konradvoelkel.github.io/ds-en/` and, in the migration dry run, at
`https://datascience.konradvoelkel.com/`.

## 5. What was decided against, for now

**"Stochastics".** The critique is right that the word is a niche term in English where
*Stochastik* is standard in German, and this is the one point where the English edition
faces a question the original never had. Against changing it: `TERMINOLOGY.md` makes it
binding, and it is load-bearing — the book needs a name for the field containing both
probability theory and statistics, and the opening figure of `intro-stochastics.md` is
about exactly that containment. A possible middle path, not taken yet: the part titles
live only in `myst.yml` and are not block-aligned with anything, so they could say
"probability and statistics" while the running text keeps the term. The cost is that part
titles are also the printed part headings.

**The project title.** `Data Science Lecture Notes from Konrad Völkel` is the PDF's
`\title{}`, and the author already appears as the byline. The German original is simply
`Data Science Vorlesungsskript` — the author's name in the title is an addition of this
edition, translating nothing. Changing it is cheap and alignment-free; it has not been
done because it renames the book.

## 6. What *was* changed in the text

On Konrad's decision of 2026-10-14, the landing page no longer addresses the Düsseldorf
BSc: named courses of that curriculum, its module handbook, its master's programme and
its "three semesters" of prerequisites were generalised to what they mean. Eight blocks
were rewritten in place, so block alignment is untouched and the staleness check cannot
see the difference — which is precisely why the divergence is tabulated in
`sync/notes/landing-page.md.md`. The rule itself is in `TRANSLATION.md` §2; the note at
the foot of the landing page still says where the book comes from, because provenance is
not courseware.

## 7. The third critique (2026-10-15), and what came of it

Checked against the live site, as before. Three of its claims do not hold: it asks to
verify a `<meta http-equiv="refresh">` stub that does not exist (GitHub issues a real
301, path-preserving — verified); it prescribes Cloudflare Bot-Fight and Caddy
`handle_errors` settings for a site that runs on neither (`server: GitHub.com`, `via:
varnish`), and reads a `PERMISSION_DENIED` from its own tooling as a property of the site;
and it asks for `alt` attributes that were added the day before. It also proposes adding
notebook downloads, which 29 chapters already have — `/build/kmeans-….ipynb`, 1.66 MB,
served as `application/x-ipynb+json`.

What it got right, and what was done:

* **A custom 404.** GitHub was serving its own "Page not found · GitHub Pages" with no
  way back into the book. `_site/404.html` now ships with the site, self-contained: no
  stylesheet, no script, no image, because MyST fingerprints asset names and any
  reference would rot silently. Its links are absolute, because GitHub Pages serves it
  under paths of arbitrary depth.
* **The course diagram is a real image now.** `tools/course_diagram.py` draws
  `images/course-structure.svg` from the same structure the mermaid block described. The
  static HTML had an empty `<figure></figure>`; it now carries an `<img>`, an `alt`
  describing the seven parts in order, and a caption. Mermaid could not take a
  `:caption:` (tested), and pre-rendering it would have pulled headless Chromium into the
  build for one picture. The SVG follows the reader's light/dark setting.
* **`llms.txt`, `llms-full.txt`, and Markdown per chapter.** `tools/llms_txt.py` writes
  each chapter's source to `<slug>.md` and `<slug>/index.md`, adds
  `<link rel="alternate" type="text/markdown">` to every page, and builds both index files
  in reading order. Written as a tool rather than the inline shell that was suggested,
  which had three faults: chapter titles live in YAML frontmatter and not in a leading
  `# ` line, so its `grep` would have labelled every entry with a slug; the landing page's
  source is `landing-page.md` while its URL is the site root, which its loop did not
  handle; and it sed-ed a multi-kilobyte payload into `</head>`.
* **The PDF.** `pages.yml` now installs TeX and builds `myst build --pdf` *before* the
  HTML build — MyST attaches the finished export to the site and renders the download
  button from it, so the order is the whole trick. The step is allowed to fail: a book
  this size has many ways to upset latexmk, and a broken PDF must not take the website
  down. When it fails the deploy logs a warning instead of leaving it to be discovered by
  a student who wanted the download. 318 pages, 19 MB, built and checked locally first.

*Correction, same day.* The first CI build of the PDF produced an 84 kB stub: xelatex
cannot include an SVG, the runner had ImageMagick but nothing for it to delegate
rasterisation to, and latexmk's force mode reported success anyway. Fixed with
`librsvg2-bin`, plus a floor that deletes an implausibly small PDF before the HTML build
so no download button is attached to it. **The commit message for that fix guesses that
the German original has the same gap. It does not.** Its figures in those chapters are
PNGs with German labels; this edition redrew them as SVG in order to relabel them in
English, which is why only this edition needs an SVG converter. Checked:
`ds-skript/images/` contains exactly one SVG, the logo, and it is not in the PDF.

And one thing the critique could not have known to ask for: `tools/check_pdf_articles.py`,
ported from the original. `myst.yml` holds the book's structure twice — once as the toc,
once as the PDF's article list — and a chapter present in one but not the other is
invisible in the printed book with nothing to say so. The original was bitten by this
twice. Publishing a PDF without that guard would have imported the trap along with the
feature.

## 7b. hreflang (2026-10-15)

Both editions now link to each other, so the language pair could finally be declared.
This edition's half ships: three tags per page -- the German counterpart, a
self-reference, and `x-default` pointing at the English edition, which is the one that
serves readers whose language matches neither.

The pairing is not guessed. `sync/filemap.json` already maps every German source file to
its English counterpart; it is what the staleness tooling runs on and what CI checks, and
chapter-to-chapter hreflang is that mapping rendered as link tags. The slugs genuinely
differ -- `kovarianz` against `covariance` -- which is the case hreflang exists for. All
30 German targets were fetched once and answer 200.

`tools/hreflang.py` refuses rather than guesses: it will not run before the canonical
exists, it will not emit a self-reference that disagrees with the canonical, and it stops
if two English pages claim the same German counterpart. The deploy then counts three tags
per page and checks the German URLs are unique, because a cluster missing its
self-reference is discarded whole and a duplicated counterpart poisons both clusters.

**What CI here cannot check is the half that matters most.** A one-sided hreflang is
ignored, and the German side's tags live in ds-skript. `tools/hreflang.py --verify`
fetches the German pages and reports how many pairs are actually bidirectional; it is
deliberately not in CI, because it would make every deploy depend on a server that
GitHub's runners already cannot reach reliably. Run at the time of writing it says
`0/30`, which is correct: ds-skript has not landed its half yet. Publishing ours first
costs nothing -- an unmatched declaration is ignored, not penalised -- and the pair starts
counting the moment the other side appears.

## 7c. Figure descriptions (started 2026-10-16)

Every figure this book draws — 156 of them — offered `<Figure size 2000x2000 with 2 Axes>`
as its text alternative. That is worse than an empty `alt`: a check for "is alt missing?"
passes cleanly while a screen reader reads out nonsense and image search finds nothing.
All the accessibility work of 2026-10-15 (§3b) was about the handful of static images and
missed this entirely, because the figures are notebook *outputs*.

MyST takes an output image's `alt` from that output's own `text/plain`, and matplotlib
writes its repr there. The German original tried every other route first — cell metadata
in five spellings, `:alt:` on a `{figure}` directive wrapping a captioned code cell — and
this version of MyST ignores all of them. So the truth lives in `alt-texts.yml` and
`tools/alt_texts.py --apply` writes it into the notebooks. Re-executing a notebook undoes
it, which is why CI checks.

Set up and finished here on 2026-10-16. All 156 are written, and the result was measured
rather than assumed: across the 30 built pages there are 226 images, **none without an
`alt` and none still carrying the matplotlib placeholder**.

They are translations of the original's, which describe the same plots. That is defensible
because the random seeds are fixed: a figure pair was extracted from both editions and
differs only in the language of its title, the axes already being labelled in English on
both sides. The pairing is by cell id, and all 116 cells resolve.

Three differences from the original's version, all deliberate:

* **Two gates rather than one.** `--check` fails only on drift, which is what a
  part-finished chapter needs; `--complete` also fails on a figure without a description.
  CI runs `--complete` now that the work is done. The distinction earned its keep the same
  day: it let the descriptions land in six batches without a red build between them.
* **Empty counts as missing.** Upstream looks for the matplotlib repr; an output with no
  `text/plain` at all slips through that. Four animation cells are exactly that case —
  MyST does not render them as images, which is why the built pages come out clean — and
  they are listed in the tool by name and reason rather than passed over silently.
* **`--skeleton` emits stubs** for one notebook with the drawing code as context, because
  the writing is the work and finding the cells should not be.
* **The descriptions are written, not translated.** The plots are labelled in English and
  a description has to match the picture in front of the reader, not the German sentence
  about a German picture.

Four notebooks had to be normalised first: they were nbformat 4.4 with no cell ids, and
ids are what the descriptions are keyed to, because cells move and ids do not. The ids
were adopted from the original, whose cells correspond one to one — so a figure now
carries the same id in both editions, and the two books' descriptions can be held against
each other later.

## 8. The process failure behind all of this

The original fixed its sitemap, canonical and `og:image` on 2026-10-14 (`d929f14`,
`6e75f56`, `c3e74d3`). Every one of those fixes lived in `.gitlab-ci.yml`. `sync.py`
hashes blocks of mirrored content files, so the weekly upstream check reported nothing —
correctly — and this edition kept serving a sitemap full of `localhost` URLs.

The rule that follows is `TRANSLATION.md` §9: when the pin moves or a staleness issue
opens, also read the original's log for commits touching CI, `myst.yml` and `tools/`.

## 9. The fourth audit (2026-10-16), and what it cost to act on

Measured, not reasoned about: all 30 pages fetched from the live site, Core Web Vitals
taken in a real browser, every claim below checked against the artifact afterwards.

### What held

Everything the first three rounds built. 30/30 pages 200 and server-rendered; 30
canonicals, 30 sitemap entries, all absolute and all with the trailing slash that answers
200; `robots.txt` right; a real path-preserving 301 from `konradvoelkel.github.io/ds-en/`
(§3 left this one open — it is now confirmed); a 404 that returns 404; JSON-LD parsing
with the right origin; `lang`, viewport, one `<h1>` per page and **zero skipped heading
levels** across all 30; 226 images with no missing `alt` and no matplotlib placeholder;
mobile clean, with code blocks scrolling inside their own `overflow-auto` parents; CLS 0.

**And the hreflang pair is live: `tools/hreflang.py --verify` now says 30/30
bidirectional.** §7b recorded `0/30` because ds-skript had not landed its half. It has.
Nothing here had to change for that; the declaration published in advance simply started
counting.

### What was actually wrong

**The figures, which is where the whole budget went.** 197 distinct images, 21.3 MB. On
`descriptive-statistics` the measured LCP was **2712 ms against a 2500 ms budget** on a
fast desktop with a warm CDN, and the LCP element was `ds-process-oneill.png`: 3678×2259
and 5.79 MB, rendered at 480×295. Total transfer for that page, 7.99 MB over 43 requests.

Three separate causes, and the second is the one that mattered most:

1. *Oversized sources.* Five images served at more than twice their display size; one at
   1432×513 shown at 54×19.
2. *RGBA.* Matplotlib writes an alpha channel the plots do not use, and PNG compresses
   four channels far worse than one. One 790 kB figure has **232 distinct colours** — as a
   palette image that is not an approximation, it is the same bytes-for-pixels picture at
   a quarter of the size.
3. *Preload.* MyST emits `<link rel="preload" as="image">` for **every** figure on the
   page — twelve on kmeans. That, not the absence of `loading="lazy"`, is why a chapter
   fetched its whole figure set before the load event. Adding the attribute alone would
   have done nothing at all: a preloaded image is fetched regardless, and the preload
   wins. The two had to move together.

Result: `images/` 9.0 MB → 3.6 MB, the build's figures 9.0 MB lighter of 23.2 MB, and the
on-load image payload of `descriptive-statistics` 6.4 MB → 1.66 MB.

**Google Fonts, imported from our own stylesheet.** Line 3 of `_site/custom-style.css`.
Three costs, and the third is the embarrassing one: a three-deep render-blocking chain, a
third party on every page view, and the precise arrangement LG München I awarded damages
over in January 2022 — in a book with a GDPR chapter that cites noyb. Self-hosted now;
`_site/fonts/PROVENANCE.txt` has the files, hashes, licences and the reasoning, and the
deploy fails if a `https://fonts.googleapis.com` reference ever comes back.

**The title suffix.** `- Data Science Lecture Notes from Konrad Völkel` is 48 of the ~60
characters a SERP renders, and on **29 of 30 pages it was truncated away entirely** —
paying nothing, spending two thirds of the line, and inviting Google to rewrite the title
rather than show it. Chapters now carry their own title alone; the landing page keeps the
book's.

*Correction to the audit that prompted this.* It also said the suffix ate into four
chapter titles. It did not: those four are over 60 characters by themselves, and since
the chapter title comes first a suffix cannot push it out — only fail to fit after it.
Konrad's decision of 2026-10-15 to leave those four (§4) is untouched and unaffected.

**`og:url` and `og:site_name`, absent on all 30.** MyST writes `og:title`,
`og:description` and `og:image` and stops.

### The trap in doing it

Editing `<title>` in the markup fixed nothing a browser would see. The page is a Remix
app: the whole document is serialised a second time into `window.__remixContext`, and on
hydration the theme re-renders the title from *that*. The server-rendered head and the
hydrated head then disagree — and Google renders before it indexes, so the copy that
loses is the one we edited. Caught by loading the built page rather than grepping it.

`tools/head_meta.py` therefore blanks `project.title` in the payload too, for chapters
only, and `pages.yml` fails the deploy if a payload could put the suffix back. The logo,
the sidebar, the part names and the previous/next footer labels were all checked in a
browser afterwards: they come from their own fields and still render.

`site.title` in `myst.yml` was the obvious alternative and was tested — it does set the
HTML title independently of `project.title`, so it would not touch the PDF. It is not used
because it is a single string doing two jobs: it becomes the chapter suffix *and* the
landing page's entire title, and those want different lengths.

### What was deliberately not done

* **WebP.** Measured at 89% off a representative figure against 57% for palette PNG. Not
  taken, because the filename would have to change and the filename appears twice per
  page — in the `<img>` and inside the hydration payload. Get that half-right and the
  server-rendered page is fine while the hydrated one 404s every figure: invisible to a
  crawler, obvious to a reader. The half of the win that needs no reference rewriting
  went first.
* **The logo** — at the time of writing. It was left for Konrad to decide and he decided
  the same day: see §9c.
* **Blocking the PDF from the index.** See §9b.
* **The third-party CSS** — at the time of writing. Done the same day instead: see §9d.

### 9b. The PDF, and what `Disallow` actually does

The audit's own phrasing — that `Disallow: /build/*.pdf` would keep the PDF "out of the
index while keeping the download working" — **is wrong, and worth correcting here rather
than quietly dropping.** `robots.txt` governs *crawling*, not *indexing*. A URL that is
disallowed but linked can still be indexed, as a bare URL with no description; Google
calls it "indexed, though blocked by robots.txt". And the site links the PDF from every
chapter's download button, so that is exactly the case that would arise.

The tool that actually prevents indexing is `X-Robots-Tag: noindex` in the HTTP response,
which requires crawling to be *allowed* so the header can be read. **GitHub Pages cannot
set response headers at all**, so that tool is not available here — a real cost of the
hosting decision in §3, alongside the 10-minute `max-age` on fingerprinted assets.

What `Disallow` would genuinely buy is narrower: Google could not read the PDF's contents,
so the PDF could not rank *for the text of the book* against the HTML chapters. What it
would cost is that the 19 MB download becomes invisible to anyone searching for a PDF of
the book, and that the URL may still surface, stripped of everything useful.

Not done, on that reading: a duplicate that cannot be described is a poor trade for a
download students actually use, and Google has handled PDF-beside-HTML for twenty years.
If it ever does start outranking the chapters, the lever is two lines appended to the
`robots.txt` rewrite in `pages.yml` — the file is already post-processed there — and it
can be added the day there is evidence for it.

### 9c. The logo, rastered (2026-10-16, same day)

The figure work left `images/logo-wide.svg` as the largest single asset on the site:
**437 kB**, one of its seventeen paths being 117 kB of coordinates on its own, loaded on
all thirty pages, and about a quarter of what `descriptive-statistics` fetches before the
load event.

**It renders at 72 × 36 CSS pixels.** The theme pins `height: 36px`, and that was measured
at desktop and mobile widths and with the mobile menu open — it is 72 × 36 everywhere. So
the squeeze was never the right move: `svgo --precision 2` reaches 162 kB but shifts 7% of
pixels visibly even at display size and rewrites the `<text>` elements; precision 3 is
clean and still leaves 297 kB. Both are a lot of Bezier curves for a thumbnail.

Konrad's decision: keep the SVG as the source, serve a raster. `tools/logo_raster.py`
renders it to `images/logo-wide.png` at **216 × 108** — 3× the display box, so a 3×-DPR
phone maps one image pixel to one device pixel — and `myst.yml` points `site.options.logo`
at the PNG. 437,307 bytes → 18,150 on disk — but **on the wire 122,702 → 18,150, which
is ~105 kB and 85% off every page, not 96%.** An SVG is text and is served gzipped; a PNG
is already compressed and gzip does nothing for it, so the compressed pair is the honest
one to quote. Confirmed against the live site rather than computed: the on-load image
payload of `descriptive-statistics` fell by 107,477 bytes across this change, which is the
logo and nothing else.

Three things worth recording:

* **The aspect ratio had to be the SVG's, not the old PNG's.** `images/logo-wide.png`
  already existed — 609 × 417, the same drawing cropped tighter, unreferenced in the whole
  of the repository's history. Handing the theme that framing would have changed the
  logo's rendered *width* from 72 px to 53, because the height is what is pinned: a layout
  change wearing an optimisation's clothes. The generator asserts the SVG's viewBox still
  matches the raster's shape, and fails rather than squashing the drawing. The old crop is
  overwritten; it is in git history, and it was never served.
* **Exact, not smallest.** Four encodings were measured by compositing each over white
  *and* over the dark navbar colour and diffing against the same composite of the SVG:
  RGBA PNG 18,150 (exact), palette PNG 5,868 (up to 36/255 off), lossless WebP 13,890
  (exact). The palette version keeps a working alpha channel and is a third of the size,
  but this drawing has gradients — the globe is three radial gradients — and that is where
  36 levels show as banding. For the book's mark, on every page, exactness is worth twelve
  kilobytes. Checked afterwards in a browser in both colour schemes: transparency intact,
  no white block in dark mode.
* **`--verify`, not `--check`, and stdlib only.** Same distinction `social_card.py` draws,
  and for the same reason: the file is *rendered*, through librsvg or Inkscape against
  whatever cairo and system fonts a machine has, so a byte comparison in CI would fail for
  reasons that are not the logo. CI asserts what no renderer can disagree about — present,
  216 × 108, a PNG colour type that can hold transparency, aspect still matching the
  source — by reading the IHDR with the standard library, because `checks.yml` runs that
  step before anything installs Pillow. Both failure modes were tested by breaking the
  file on purpose: a flattened logo and an undersized one each fail with the reason.

`tools/optimize_images.py` needs no exception for it. The alpha channel is genuinely in
use, so the file never reaches that tool's palette branch, and plain recompression gains
less than its floor — checked rather than assumed.

**The German edition serves the byte-identical 437 kB SVG** (same sha, same path hash
under its own build). Passed upstream.

### 9d. The theme's own three stylesheets (2026-10-16, same day)

The last third parties on the page. Every page view fetched

    cdn.jsdelivr.net/npm/katex@0.15.2/dist/katex.min.css
    cdnjs.cloudflare.com/ajax/libs/font-awesome/4.7.0/css/font-awesome.css
    cdn.jsdelivr.net/npm/jupyter-matplotlib@0.11.3/css/mpl_widget.css

all three render-blocking, none preloadable — a stylesheet is discovered before its own
contents are — and on any page with mathematics up to twenty KaTeX font files from
jsdelivr behind them, nine of them on `expectation-variance`, pulled relative to that
stylesheet's own URL.

Same argument as the Google Fonts `@import` in §9, one step further out. The difference
is whose markup it is: the `@import` was line 3 of our own stylesheet and could be
deleted, these are the theme's `<link>` tags, so they are rewritten after the build by
`tools/vendor_assets.py` and the files are committed in `_site/vendor/` — 28 files,
480 kB, unmodified, with hashes and licences in `PROVENANCE.txt`.

Four things worth recording:

* **Font Awesome looks unused and is not.** Across all thirty built pages there is not one
  element with a `fa-` class, and the browser reports the face as `unloaded` on every one:
  the stylesheet is fetched and the font it asks for never is. The obvious move on that
  evidence is to delete the link. It would have been wrong — the theme's client bundle
  contains `"fa fa-"` with `fa-play`, `fa-stop`, `fa-pause`, `fa-check`, `fa-times`,
  `fa-caret` and `fa-retweet`, which are thebe's run/stop/restart controls, and they
  appear only once a reader makes a notebook live. Deleting it would have left blank
  squares in the one feature that needs legible buttons. Vendored instead, and the path
  was then tested directly rather than by reasoning: an element with `class="fa fa-play"`
  injected into a built page loads the face from `/vendor/...woff2?v=4.7.0`, 200, and the
  glyph renders.
* **The URLs are in the client bundles as well as the HTML** — `root-*.js` and two shared
  chunks. Rewriting only the server-rendered markup would have the page load correctly and
  then, on hydration, re-add the CDN links, fetching both copies: worse than before, and
  invisible outside a network panel. The same trap as the title in §9, and found the same
  way — by loading the rewritten page instead of grepping it. The rewrite covers `.js`.
* **The vendored CSS is byte-exact, and provably so.** MyST emits the KaTeX link with an
  SRI hash; the vendored copy's `sha384` matches it exactly, so the file is demonstrably
  the bytes the site was already serving. The `integrity` and `crossorigin` attributes are
  dropped on rewrite anyway: a hash pinned to a file that now lives in this repository is
  a tripwire for whoever next updates it, since a mismatch does not fail loudly, it just
  blocks the stylesheet and loses the mathematics with nothing in the build log.
* **What this does not do, stated narrowly.** The two CDN hostnames still appear in
  `thebe-lite.min.js`, `thebe-core.min.js` and one shared chunk: Pyodide, MathJax 2.7.5
  and require.js, fetched only when a reader starts a live kernel. Pyodide alone is tens of
  megabytes before any package and is not vendorable. So: **reading the book now contacts
  no third party; running the code in it still does.** The deploy guard greps for the three
  stylesheet URLs and not for the hostnames, because a guard written against the hostnames
  could only ever be satisfied by deleting thebe.

Measured on the built artifact before committing: on `expectation-variance` — 502 maths
nodes, the heaviest in the book — **zero third-party requests**, all nine KaTeX faces
served from `/vendor/katex/fonts/`, no failed requests, and the formulae set in
`KaTeX_Math` rather than a fallback.

`tools/vendor_assets.py` fails rather than falling back if the theme ever asks for a
different version, and names both versions when it does. The tempting behaviour — leave an
unknown version pointing at the CDN so the build keeps working — would silently restore
exactly what this removed.

## 10. Freshness, ported from the original (2026-10-16)

The first thing to travel **from** ds-skript rather than to it. The German edition landed
`e229a9d` after a GEO assessment of both live editions, and the measurement in it was that
ds-en lacked two things that existed nowhere yet — not forgotten, just built there first.

Re-measured here against the live site before porting anything, as this file requires:

```
article:modified_time         0 of 30 pages
<lastmod> in sitemap.xml      0 of 30 entries
dateModified in the JSON-LD   absent (and no datePublished either)
```

All three confirmed. Recency is one of the strongest selection signals for AI answer
systems, the book is maintained continuously, and not one page said so. It weighs more
here than in the original: this is the edition that is supposed to travel, and the domain
has only served since 2026-10-15, so there is no crawl history for anything to infer a
cadence from.

`tools/freshness.py` is ported essentially as it stands: the date per page from
`git log -1 --format=%cI -- <source>`, **not** from the build clock, and therefore with no
fallback to the clock — if git has nothing, it stops rather than invent. It writes
`article:modified_time` into each `<head>` and `<lastmod>` into each sitemap entry, keyed
on the last path segment of the `<loc>` so that it does not care whether the origin rewrite
runs before or after it.

### The trap applied, but not in the way the original describes — and that mattered

`fetch-depth: 0` is now on the pages checkout, with the reasoning written beside it,
because the whole point of the original's `GIT_DEPTH: "0"` note is that someone will
otherwise trim it back in a year.

But the handover said a shallow clone makes the script abort, and **it does not, on this
platform.** Tested rather than assumed, in a real `git clone --depth 1` of this
repository: `actions/checkout` fetches exactly one commit, and against a commit with no
parent git reports *every* file as modified by it. So `git log -1 -- <file>` answers for
all thirty files — with HEAD's timestamp — and the script reports success:

```
30 pages dated, 30 sitemap entries with <lastmod>; newest change 2026-10-16
    -> all 30 dated 2026-10-16T10:18:10+02:00, the deploy commit's own second
       (the real dates span 2026-10-14 to 2026-10-16)
```

That is exactly the build-time date the whole design exists to refuse, reached by the one
route the upstream guard does not cover, and silent — the output is indistinguishable from
a correct run. Upstream's "git returns nothing" case is real but is GitLab's: under
`GIT_DEPTH: 20` a file untouched for twenty commits genuinely has no entry.

So `freshness.py` here gains a `refuse_shallow()` that asserts
`git rev-parse --is-shallow-repository` up front, before reading a single date. Both
directions tested: it aborts in the depth-1 clone with the `fetch-depth: 0` fix in the
message, and passes in the full one. **This is the one thing that is not a port**, and it
is in `UPSTREAM-NOTES.md` — ds-skript is not exposed to it today, but it would be the
moment that job moved to GitHub Actions, and that is a one-line change away.

### The decision this edition had to make

**The date is the translation commit's, not the German original's.** The page at this URL
changed on the day it was translated or revised; `<lastmod>` tells a crawler when to come
back for *this* URL, and the German date would announce a change that did not happen here
and would sometimes date a page to before it existed. The alternative — carrying the
original's dates across `sync/filemap.json` — would also make these dates depend on a
server CI already cannot reach reliably, which is why `checks.yml` stopped cloning it.

The honest cost: a commit touching only this edition refreshes the date although the
substance did not move. Today's KaTeX fix is exactly that case. It is still not a false
claim — the page did change — and the opposite error, a page silently keeping a date from
before it was rewritten, is the worse one.

### One thing sent back the other way

`inject_jsonld.py` here dates the book by `freshness.book_date()`, the newest change
anywhere in it, not by the landing page's own stamp. The original takes the landing page's
stamp, which dates a `@type: Book` entity by one of its thirty pages — visible on the first
run here, where the landing page last changed on the 15th and nineteen chapters on the
16th. `book_date()` exists upstream and is used only in a log line, which reads as the same
intention, arrived at and not wired up. In `UPSTREAM-NOTES.md`.

### Deliberately not done, because the assessment asked for none of it here

* **Nothing to `robots.txt`.** The assessment's load-bearing finding is the German
  edition's alone: its `robots.txt` sits under `/ds-skript/` and therefore does not apply
  at all, the host root being a GitLab login redirect. Ours is at the domain root and
  measured sound — `Allow: /`, correct `Sitemap:` line.
* **No `llms.txt`.** Shipped here since 2026-10-15 (§7).
* **No `FAQPage` markup.** Google switched the FAQ rich results off on 2026-05-07.
* **No 150-word chunking of chapters.** Google's own AI guidance of 2026-05-15 says
  explicitly that content need not be chunked for AI search.
* **No visible date on the page.** The theme re-renders the page header from the hydration
  payload, so a line written into the markup is gone after hydration — the trap in §9. The
  clean route is `date:` in each chapter's frontmatter, which is a source change across 30
  block-aligned files and waits to be asked for.

### Also noted for the next sync

`llms_txt.py` differs: ds-skript's reads the built `config.json`, ours reads `myst.yml`.
Upstream's reason is that its CI container has no PyYAML; ours does, so the constraint is
absent. `freshness.py` nevertheless reads `config.json` as the original does — it is the
build's own account of what it built, so a drift between toc and artifact surfaces as the
mismatch it is, and the step needs no dependency. Aligning `llms_txt.py` the same way is
open and costs nothing but a commit.

ds-skript has no counterpart to `head_meta.py`; that is known there and decided separately.

### Measured on the artifact, in job order

```
30 of 30 pages with article:modified_time
30 of 30 sitemap entries with <lastmod>
JSON-LD dateModified 2026-10-16T07:50:15+02:00  (the book's newest change)
dates genuinely per page: 7 on 10-14, 4 on 10-15, 19 on 10-16
hreflang --verify  30/30 bidirectional, unchanged
```

The hreflang point was checked rather than assumed: `--verify` matches `hreflang=`
immediately after `rel="alternate"`, and the Markdown alternate carries no `hreflang`, so
the four `rel="alternate"` links per page do not collide. 90 tags, as before.

## 11. Six formulae that never rendered (2026-10-16)

`sync/handover-ds-skript.md` was rewritten four hours after it was written, because four of
its items were already wrong: ds-skript had landed `alt` texts, the mermaid diagram, the
social card and — adopted from here — `refuse_shallow()` and the `_git()` helper. The
instruction in the file to re-measure before acting is the only reason that was caught, and
it is the reason it stays at the top.

Two things came back the other way in `dedfd0b`, both worth having here eventually:

* **`--stamp-source` puts a visible date on the landing page** by writing the frontmatter
  before the build. §10 recorded that a visible date was "not included" here because the
  theme re-renders the page header from the hydration payload and markup is lost — true,

  edition's reason for not having one.
* **Their landing page's `article:modified_time` is the newest of all pages**, not its own,
  and `inject_jsonld.py` reads the work's date back from there. This edition keeps that tag
  per-document and imports `book_date()` for the JSON-LD alone. Both reach the same
  `dateModified`; the divergence is whether a title page's meta tag may speak for the book.
  Defensible either way, recorded so it is not mistaken for drift.

### 13b. A destructive mistake made from this repository

While testing the authentication branch of `upstream.yml` (§12b), the clone step was
extracted to a script and run with a stubbed `git` that always failed, in order to exercise
the failure path. That path ends in `rm -rf ../ds-skript`. The working directory was
`ds-en`, so it resolved to the real German repository, and deleted it. The tracked content
came back from the remote; four weeks of gitignored working notes under `todo/` did not,
and were reconstructed from transcripts. `todo/` is now a symlink to `~/notizen/`.

The stub covered `git`. It did not cover `rm`. The specific error was running a failure
path on purpose without first reading it for destructive commands — the target of an
`rm -rf` has to be looked at *before* it is made reachable, and a relative path in a script
means the target depends on where it is run from.

`upstream.yml` now constructs its clone directory under `RUNNER_TEMP`, never a sibling of
the checkout, and refuses to `rm -rf` anything whose path does not end in its own directory
name. That is the fix for the script. The rule for whoever tests one next: a stub that
forces a branch is not a sandbox, and a dry run is only dry if every destructive command in
the reachable path has been read first.

## 14. `--stamp-source`, and two guards learned from upstream (2026-10-16)

ds-skript worked the whole handover in ten commits — formulae, Google Fonts, logo raster,
`og:url`, lazy figures, PNG re-encoding, the three CDN stylesheets. Three of those commits
are new findings rather than ports, and two of them land here.

### The visible date, ported the other way

§10 recorded that a visible date was "not included" because the theme re-renders the page
header from the hydration payload, so markup written after the build is lost. True, and the
wrong conclusion: ds-skript's `--stamp-source` writes `date:` into the landing page's
frontmatter *before* MyST runs, so it travels in the payload and survives. Their solution
is better than this edition's reason for not having one, and that is the first thing to
travel in that direction on its own merits rather than as a correction.

Verified in a browser on the built artifact: `October 16, 2026` renders under the byline as
`<time class="myst-fm-date-string">` and is still there after hydration.

Three things kept from their design, one cost that does not apply here:

* **The landing page only.** A project-level `date` in `myst.yml` prints the same day on
  all 30 pages, and most would then assert a date their source does not support. On a title
  page "as of" is true of the edition as a whole.
* **The day, not the second.** A timestamp on a title page is noise.
* **It reads `myst.yml`, not `config.json`**, unlike everything else in `freshness.py` —
  forced, because it runs before the build and `config.json` is an output of the build.
* The cost they paid knowingly — the theme formats the date in hard-coded English,
  `language: de` does not change it, a German string is silently dropped — is simply the
  right format for an English edition.

The stamp is **not committed**: CI writes it, the repository does not carry it, exactly as
ds-skript does. A committed date would be stale the moment it was written.

### The pipefail trap, avoided rather than repeated

`081a7a9`: their formula guard went red precisely when it should have passed. GitLab runs
scripts under `set -eo pipefail`; `find -exec grep +` exits 1 when grep matches nothing,
and *nothing* is the good case here. The assignment aborted before any message.

GitHub's default shell is `bash -e` **without** pipefail, so the naive form survives here —
checked both ways rather than assumed:

```
set -eo pipefail   naive form, zero broken formulae  -> exit 1, no output
set -eo pipefail   { ... || true; } | wc -l          -> n=0, exit 0
set -e             naive form                        -> n=0, exit 0
```

The formula guard is now in this deploy too, written with `|| true` so it does not depend
on that default: one `shell: bash` anywhere in the file would arm it.

### The CSS asset guard, including the mistake it taught

`09cf4de`: ds-skript lost its webfonts to a relative `url()` that resolved against the
wrong one of two copies of the same stylesheet. This edition was never exposed — `__BASE__`
is substituted rather than a relative path used — but the *vendored* stylesheets were
unguarded, and KaTeX naming its fonts `fonts/X.woff2` couples the vendor layout to the CSS.

The first version written here made exactly the mistake their commit message describes:
requiring every `url()` to resolve flagged **45 references on a correct build**, because
only the woff2 is vendored and the `.woff`/`.ttf`/`.eot`/`.svg` lines are deliberately left
in the upstream CSS. A guard nobody can satisfy is a guard everybody learns to ignore. The
rule is one resolvable source per `@font-face`, and each `url()` outside a face resolving on
its own.

Scoped to what this repository owns. Sweeping all built CSS turns up
`/myst_assets_folder/_assets/plotly-*.svg` in four of MyST's own theme bundles — an
unrewritten placeholder, upstream's and not ours to fix, and flagging it would be the
unsatisfiable guard all over again. **Worth passing to ds-skript, whose version sweeps more
broadly and will meet it.**

Both directions tested: a `@font-face` whose sources all vanish fails; the healthy build
passes. The existing count guard catches a missing file, this one catches a CSS-to-layout
mismatch — different failures, both real.

## 15. The edition never hydrated, and that invalidates several entries above (2026-10-17)

Not found by an audit. Konrad asked why the German edition scaled worse on phones than this
one; measuring both at 375 px turned up a 613 px page in *both* editions (§15b), and, in
passing, that this edition loads 6 stylesheets where ds-skript loads 12. That difference is
the entry point to everything below. **The edition that looked healthier was the broken one.**

### The bug

`strip_payload_title` ended with:

```python
payload, length = json.JSONDecoder().raw_decode(doc, start)
...
return doc[:start] + out + doc[start + length:]
```

`raw_decode` returns the index in `doc` where the JSON ends, not how many characters it
consumed. `start + length` therefore points past the end of the document and the tail slice
evaluates to `""`. Everything after the hydration payload was dropped, on every page, from
the moment this function landed.

That moment is precise and it matters: `9e655a6`, 2026-10-16 09:28 — the fourth-audit commit
that introduced the function. Before it the edition hydrated normally. It was broken for
15 hours and 16 commits, until `b2dd473` the following night.

**What that cost, exactly: 315 characters per page.** Measured by running the committed
version before and after the one-line fix against the same input: 971,062 against 971,377
bytes. Those 315 characters are `;</script>`, the whole `<script type="module">` that boots
the client, and `</body></html>`.

The commit that fixed it (`b2dd473`) says "about 85 kB" and that is wrong — a figure worth
correcting here because this file is only useful if its numbers are. The 84,747-character
difference from the raw build is `strip_payload_title`'s compact re-serialisation of the
payload, which happened in the broken and the fixed version alike. The damage was never
about size. It was about *which* 315 characters.

Nothing looked wrong, which is why sixteen commits passed over it: browsers close
unterminated tags and render the page exactly as intended. There was no console error, no
layout shift, no missing content. The only visible trace was a stylesheet count nobody had
reason to compare.

### What it invalidates above

From 09:28 on 2026-10-16 this edition did not hydrate, so every argument written after that
which turns on what hydration does was reasoning about something that had already stopped
happening. Checked against the commit times rather than assumed:

* **§9, the title suffix** (`9e655a6`, 09:28). The one case that was *correct when written*:
  hydration did re-render the title from the payload, right up to this commit. Then the fix
  broke hydration as a side effect and so removed its own reason to exist, within the same
  commit. The markup edit was doing the work from then on.
* **§9d** (10:18), **§10** (10:32), **§13** (13:53) and **§14** (16:20) were all written
  after 09:28, so their hydration reasoning was already untrue when it was written.
* **§9, WebP declined.** Rejected partly because a renamed file "appears twice per page — in
  the `<img>` and inside the hydration payload", and a half-done rename would 404 after
  hydration. That risk never existed, and with §15a the payload is gone outright. **The WebP
  decision is reopened on its merits** — measured at 89% off a representative figure.
* **§9d, the CDN stylesheets.** "Then, on hydration, re-add the CDN links" could not happen.
  Vendoring them was still right, because the links are in the server-rendered HTML too.
* **§10, §13, §14, the visible date.** §10 gave hydration as the reason not to have one; §14
  ported `--stamp-source` and reported it "verified in a browser ... still there after
  hydration". That verification ran at 16:20, seven hours after hydration stopped, so it
  could not have tested what it claims. The date does render, for a simpler reason: nothing
  ever replaces it. The port stands; the evidence given for it was vacuous.

None of these conclusions flip. Several were right for the wrong reason, which is its own
kind of finding — and the sharpest version of it is §9: a fix that invalidated its own
premise in the act of being applied, and then went on being cited as the reason for things.

### 15b. The 613 px page, which was never a German problem

`descriptive-statistics` measured 613 px at a 375 px viewport in both editions. Not the table
— that sits in a `div.overflow-auto` and scrolls inside its own box — but two long formulas
*inline in a list item*: `span.katex` is inline, and inline elements honour neither
`max-width` nor `overflow`, which is why selectors on `.katex-display` or a `max-width` on
the ancestors do nothing. Fixed in both editions (`16eeb49` here) by letting the surrounding
element scroll.

The obvious `.katex { display:inline-block }` was measured and rejected: it fixes the width
but makes every inline formula 2 px taller, which on a formula-heavy chapter is +2482 px of
page height — uneven leading everywhere maths appears in running text. The chosen rule costs
+48 px.

**A measurement trap worth keeping.** A bare `myst build` leaves out the KaTeX fonts that the
workflow copies in, and reports 379 px instead of 613. Measuring the local build alone would
have shown no bug at all. Layout questions in this repository have to be measured against a
faithful rerun of the pages job.

### The lesson

A difference between the two editions is not automatically a defect in the one that stands
out. Here the quieter number was the symptom: 6 stylesheets instead of 12 because the client
never started, because a slice overshot by `start`. Compare the editions when they disagree,
but establish which one is right before fixing the other.

## 15c. The removal that followed broke the book, and was reverted (2026-10-17)

§15 is right about the history and wrong about what to do with it. "This edition has never
hydrated, so what goes away is something nobody here has had" reads the 15-hour window as
the normal state. It was the accident. Before `9e655a6` at 09:28 the edition hydrated like
any MyST site, and the readers of those weeks had what §15a then removed.

Konrad found it the next morning: the live book was unusable. Confirmed in a browser
against the live site, and it was not only the citations:

* At phone width the hamburger is the only route to the table of contents, and it opened
  nothing. **No chapter was reachable at all.**
* At desktop width the sidebar showed only the part that happened to be open. "Machine
  learning" and every other collapsed part refused to expand — two thirds of the book
  unreachable.
* The right-hand CONTENTS outline was absent from every page.
* Citations rendered as `<cite><span class="hover-link">` with no `href`: styled like links,
  inert.

The theme's navigation is React. It needs the runtime, whatever the page looks like
standing still.

### Why the verification did not catch it

`1d04134` checked body text character for character, the `<title>`, the counts of images,
links and headings, and the scroll height to the pixel. Every one of those is a measure of
a page *at rest*. The damage was entirely in what happens when you click, so the evidence
was strong, carefully gathered, and aimed at the wrong thing. A page that renders
identically and responds to nothing passes every check in that list.

**The rule this earns:** when a change removes code that runs, the postcondition has to run
something too. For this site that means at least one click per interactive affordance — the
menu button, a collapsed sidebar part, the search box — not a diff of the markup.

Two ways to perform that badly, both found by the ds-skript agent while checking this
finding against their own edition, and both worth more than the rule itself:

* **Measuring the wrong thing after the click.** Their first attempt counted `a[href]`
  before and after, and reported "no reaction" for the *working* German page — the menu is
  already in the DOM and the click only reveals it. A functional test aimed at the wrong
  quantity is no better than a static diff. What works is the visible navigation area:
  321,784 → 517,606 px² on the German page, 320,764 → 494,828 on this one.
* **Choosing an affordance that does not need the runtime.** `<details>` kept opening with
  the bundle blocked, because it is native HTML. An element that works without the thing
  you removed proves nothing about it, and hands back a confident green.

Their causal check is the better recipe and is what this should have done in the first
place: block the bundle outright (`Network.setBlockedURLs`), then click. Navigation area
219,024 → 219,024 — no change, cause established, no inference required.

### The reason given for the removal did not hold either

Restoring the bundle was supposed to hand back thebe, and with it Pyodide, MathJax and
require.js from CDNs, in a book whose own data-protection chapter argues against that.
But **thebe is not configured in `myst.yml` at all**, so the bundle never loaded it.
Measured after the revert, with the deploy's own post-processing in order
(`vendor_assets.py`, then `head_meta.py`): 51 requests on `descriptive-statistics`,
**zero of them third-party**. The CDN exposure that removal was meant to prevent is already
prevented by vendoring, which §9d put there.

### What it costs

The payload comes back with the bundle — hydration reads it, so they cannot be separated.
That is the 59% per page returned, and it was a real gain. It is the price of a book that
can be navigated, which is not a trade worth making. If the weight is to come down, it has
to come down some other way; `.gz` beside every text file, which ds-skript added in
`11a271f`, is the obvious candidate and does not touch behaviour.

The WebP decision stays reopened: §15's argument against it was the payload rename risk,
and that risk is back. Reopened on measurement, not reinstated.

## 16. The upstream check never worked, and why the fix is a mirror (2026-10-17)

The staleness check has run on every dispatch since it was built and has **never once
succeeded**. The failures were read as flakiness, then as a network block, and the retry
loop was stretched from eight minutes of TCP timeouts to a real seventeen-minute window to
accommodate it. That was the right fix for the wrong diagnosis.

Measured today, which settles it:

    GET /voelkel/ds-skript                            -> 200
    GET /voelkel/ds-skript.git/info/refs?service=...  -> 401
    API visibility                                    -> "public"

The HHU GitLab serves the project page to a stranger and refuses the git endpoint to
anyone not logged in. The project is public to read and closed to clone. No retry strategy
survives a 401, and the clones that succeed from Konrad's machine succeed only because
`git-credential-libsecret` supplies stored credentials — which is why this took so long to
see from here.

**The fix is a public mirror on GitHub**, `konradvoelkel/ds-skript-mirror`, pushed after
every commit by a job in ds-skript's own GitLab CI. The check now clones that.

Two things about the shape of it:

* **The credential sits on the GitLab side.** ds-en could have held a GitLab token instead,
  and that was the first instinct. Pushing from upstream needs exactly one credential,
  stored where Konrad already administers CI variables, and leaves this repository with no
  secrets at all — the property §3 describes, which is what lets the whole pipeline be
  read and audited by a stranger. Keeping it was worth the extra hop.
* **A mirror that stops is worse than no mirror**, because the check would compare against
  a frozen copy and report "up to date" forever — the exact silent-success failure this
  check exists to catch. So it refuses to judge at all if the mirror's newest commit is
  more than two days old, and says which pipeline to look at.

**It works.** The mirror job landed in ds-skript on 2026-10-17 and the check ran through
for the first time in its existence: mirror HEAD 0 days old, `772d0017 → 1ed35d57`,
0 stale regions. Verified from here rather than taken on report — the mirror's HEAD equals
ds-skript's, 210 commits on both sides, and the mirror carries exactly `refs/heads/main`.

Two things the upstream agent got right that this side's skeleton had wrong, both worth
keeping in mind the next time a mirror is written: the token belongs in a credential store
rather than the push URL, because masking only catches exact matches and a remote URL
shows up in git errors and traces; and the dispatch that triggers this check must declare
`needs` on the mirror job, or the two deploy jobs race and the check judges the state
*before* the push — reporting "up to date" exactly when something has moved.

The seeding was deliberately not done from here. Mirroring means taking source that is
currently obtainable only with Konrad's credentials and publishing it anonymously; the
sandbox refused the push, and it was right to. Konrad authorised the mirror, and the first
push comes from his CI job, under his token, which is where that decision belongs.

## 17. Phase 1 of the audit of 2026-10-17, and the two things it got wrong

`datascience.konradvoelkel.com-audit/` scored the site 79/100 and put three items in
Phase 1: per-chapter structured data, stop shipping Thebe to pages with no code, and fix
the per-page `og:image`. Its `BreadcrumbList` item from Phase 2 was folded in, since it
is the same pass over the same file. All four are done. Two of them do not say what the
audit said they would, and both are measurements rather than opinions.

### Structured data: one book, 29 chapters, one author

`tools/inject_jsonld.py` now walks the whole build instead of the landing page alone.
Each chapter gets a `@graph` of two nodes: a `["Chapter","LearningResource"]` with its own
`@id` of `.../<slug>/#chapter`, `isPartOf` the single book node `.../#work`, its
`position` in the toc and `author` by reference; and a `BreadcrumbList`. The author object
on the landing page gained `"@id": ".../#author"`, so the person is one node in the graph
rather than thirty copies of a name with six `sameAs` links.

The old docstring's objection — *"repeating it per chapter would assert 30 books"* — was
right, and the audit's reply is the one that was missing: a chapter is not a book, it is a
`Chapter` of one. 1 of 30 pages carried structured data; now 30 do.

**Nothing in the node is computed twice.** The name and description are read back out of
`og:title`/`og:description`, the date out of `article:modified_time`, the licence and
language out of the book node. That is why the tool moved **after** `head_meta.py` in
`pages.yml`, where it used to run before it: the title it reads is the one with the
project suffix already trimmed, and the card it reads for the book is the one that step
has vetted. Running it first would have put " - Data Science Lecture Notes from Konrad
Völkel" into all 29 chapter names. It refuses to run if it finds either untouched, so
the order cannot drift back silently.

### The breadcrumb has two items, not three, and Google is the reason

The audit asked for book → part → chapter, and the seven part names are in the toc. There
is no page for a part, so the middle item would have had a `name` and no `item`. Measured,
rather than assumed:

* **Schema Markup Validator:** the three-item version passes. 0 errors, 0 warnings.
* **Google Rich Results Test:** *"1 invalid item detected"* on Breadcrumbs, and "invalid
  items are not eligible for Google Search's rich results". Google's documentation says
  `item` is required on every element but the last.

So the three-item trail renders no breadcrumb at all, which is the whole point of the
type. Minting `.../#part-multivariate-stochastics` to satisfy the validator would be a
fragment that is not an anchor on any page — the sitemap-pointing-at-localhost mistake in
a smaller hat. Two items it is, and the part name still reaches a reader through the
sidebar and an engine through `isPartOf` + `position`. If a part ever gets a page, the
middle item has a URL and goes back in; `chapter_graph()` still takes the part for that
reason.

### Thebe: the audit's fix was impossible, and the real one is in the client bundle

The audit said to strip a `<script>` tag for `thebe-core.min.js` from pages with no
`jp-CodeCell`. Three findings, all measured on the built pages and in the browser:

* **There is no script tag.** The only thebe reference in the markup is a stylesheet.
  `thebe-core.min.js` is appended to `document.head` at runtime by thebe-react's loader.
* **`jp-CodeCell` is not in the markup either** — thebe adds it when it attaches to a
  cell, and this site has no kernel server, so nothing ever attaches. Zero occurrences in
  all thirty built pages and in the hydrated DOM. The marker that *is* there is MyST's
  `myst-jp` class prefix: zero on exactly twelve Markdown chapters (the ten the audit
  named, plus `descriptive-statistics` and `statistical-tests`, whose code blocks are
  static), non-zero on all eighteen notebook pages.
* **It really does load everywhere**, which the audit had right. The theme's execute-scope
  provider calls `load()` from an effect with no gate on whether the page has anything
  computable. A first measurement here said otherwise and was wrong: the load fires about
  300 ms after hydration, and the network panel had been read before it.

So the 359 kB is bought back in `tools/thebe_gate.py`, which gates that one effect on
MyST's own `computable` flag in the one client chunk that has it, and fails the build if
the minified shape it is anchored on moves. Verified by loading the built site:
`thebe-core.min.js` is requested on notebook pages and on none of the twelve Markdown
chapters.

`head_meta.py` drops the two jupyter stylesheets (87 kB + 1 kB) from those twelve pages,
and that one is **honestly smaller than it looks**: the theme's root route declares them
in a Remix `links()` export, which cannot see page data, so the client re-adds both after
hydration. What the removal buys is the critical path — they are now the last two requests
of the load instead of render-blocking tags in the head. Recorded in UPSTREAM-NOTES.md.

**§15c's rule was applied, because this removes code that runs.** Not a diff of the
markup: on a Markdown chapter, with the gate in place, the mobile menu opens (20 links /
175,821 px² → 28 / 264,516), the collapsed "Machine learning" part expands (97 → 105
links, 448,577 → 542,657 px²) and ctrl+K search returns live results for "entropy". The
notebook pages still load thebe and still render their figures, 11 of 11 on `kmeans`.

### og:image: eleven pages were shipping something that is not a card

Every page declares `twitter:card=summary_large_image`, which wants 1200×630, and MyST
fills `og:image` with the page's first figure. `head_meta.py` now keeps a figure only if
it is at least 1200×630 **and** landscape, and replaces it with the generic card
otherwise: 8 of 30 pages replaced, among them `statistical-tests` (400×528, portrait),
`expectation-variance` (555×329), `intro-python` (518×588) and
`important-continuous-distributions` (1226×1648). Three pages keep a figure that is
genuinely a card: `dimensionality-reduction`, `model-selection`, `relative-entropy`.

One condition is on bytes rather than pixels, and it is a judgement: over 500 kB the
figure loses. That catches `descriptive-statistics`, whose card the audit measured at
1.2 MB — thirty times the generic card for an image that renders at the same size — and
nothing else, the next largest being 461 kB. The honest fix for both is WebP
(ACTION-PLAN 3.2), after which the threshold can rise.

The card's filename is read off the landing page rather than globbed: MyST emits the
project thumbnail **twice**, under two fingerprints of identical bytes, so "the one
social-card file" does not exist. The URL written into each page is built from the prefix
that page's own image tag already carries, so the same code is correct before and after
the step that makes those URLs absolute.

**And the markup was half the job, exactly as §1 of `head_meta.py` warns.** The first
version of this fixed only the tags; loaded in a browser, `statistical-tests` served the
card and then hydrated back to the 400×528 figure, because the theme's `meta()` builds
og:image from `page.frontmatter.thumbnailOptimized || page.frontmatter.thumbnail` in the
hydration payload. For the platforms that draw cards this changed nothing — none of them
runs the script — but Google renders before it indexes, and the trap is the one this file
has already been caught by once. The payload is now edited alongside the tags, and only
`page.frontmatter`: the `pages[]` entries in the payload carry a thumbnail each for the
hover preview of an internal link, where a portrait figure is a perfectly good picture
and thirty copies of the generic card would be a worse book. A postcondition fails the
build if the two ever disagree again.

## 18. Phase 2 of the audit (2026-10-17), and the half of it the browser throws away

ACTION-PLAN items 2.1 (`width`/`height` on every figure), 2.3 (the empty `keywords` meta)
and 2.4 (the one over-long title). All three are done, and the first one turned out to be
two jobs rather than one, for a reason that is bigger than the item: **this theme does not
hydrate, it re-renders, and about 190 ms into every page load the entire server-rendered
document is thrown away.** That is measured below, and it invalidates a sentence or two
above.

### The figures now say how big they are, in the markup and in a stylesheet

226 `<img>` across the thirty pages and not one of them declared a size, which is why
`/expectation-variance/` measured CLS 0.278 — past Google's 0.25 "poor" line — and why
Lighthouse flagged `unsized-images` on both pages PageSpeed tested. 196 of the 226 are
inside `<main>`; the rest are the navigation logo, one per page, and are not touched.

193 of the 196 now carry `width` and `height` read from the built file itself. Pillow
reads the PNGs, the JPEG and the GIF; the five SVGs are read from their root element, with
the `viewBox` as the fallback — the book's own logo is `30mm` by `15mm`, which is the case
that makes the fallback necessary rather than decorative. The numbers are the file's own
pixels and not the size the page renders: 28 figures carry an inline `style="width:360px"`
from the chapter source, so the attributes say 555×329 and the picture still appears at
360 px wide, which is exactly how the two are meant to interact.

**Three figures are deliberately left unsized**, for one reason wearing two hats: their
height is already fixed by something else, and a width next to a fixed height is the only
way these attributes can distort a picture — the aspect ratio is consulted only while one
of the two dimensions is still `auto`. Two are the inline thumbnails in
`descriptive-statistics` that sit inside a `<p>`, where the theme's
`.article p>img{max-height:1.2em}` caps them to the height of the text; the third is the
licence badge on the landing page, whose own style says `height:20px`. `head_meta.py`
names them on every run, so a fourth one is read rather than assumed.

The attributes on their own would have been theatre, and the measurement that says so is
worth more than the item that prompted it. On every page of the built site the console
carries **React error #418** — a hydration failure — and what follows is not a patch-up
but a re-render of the whole document:

* A `MutationObserver` installed before hydration sees `<main>` **removed** at 186 ms.
* `eda-examples` is served with `loading="lazy"` on 37 of its 38 figures. 300 ms after
  load the hydrated DOM has **0**.
* The hydrated `<head>` of `/covariance/` has **no** `og:url`, **no** `og:site_name`, **no**
  `rel=canonical`, **no** `hreflang`, **no** `article:modified_time` and **no** font
  preloads. Every one of them is in the file that was served. The stylesheet links are
  there twice, because the client adds its own copy of each.
* ~~It is not ours. A build with no post-processing at all throws the same #418 and ends
  up with the same duplicated stylesheets, so this is the theme, not our injections.~~
  **Wrong, and corrected in §20 (2026-10-18): it is ours, in `vendor_assets.py` and in
  section 5 of `head_meta.py`, and the theme hydrates fine without them.** The build this
  was measured on had been post-processed — `rm -rf _build/html` leaves the patched client
  chunks in the template cache, and the console was read across navigations in one tab, so
  errors from the previous page were counted as this one's. The test that settles it is
  `git archive HEAD` into its own tree, which is what §20 did. The three measured bullets
  above stand; only the attribution was wrong, and it was the one claim here that nobody
  had checked properly.

§15 of this file recorded that the edition *never hydrated* and fixed it; §17 recorded that
the theme re-renders the *head* from the payload. The honest version is stronger than
both: **nothing written into the markup after the build survives in the rendered DOM** —
true of the site as deployed, and §20 found out why and how to end it, which makes this a
defect of ours rather than the fact of life this section took it for. The
tags still reach every consumer that reads HTML without running it — which is every
platform that draws a preview card, and Google's first pass — and `tools/freshness.py`
already drew the same conclusion for the visible date, which is why that one travels
through the frontmatter instead. But a claim of the form "the browser ends up with X" needs
checking against this, and several above were written before anyone looked.

### So the sizes are in `myst-theme.css` as well, in a cascade layer

The second copy goes where a re-render cannot reach: `myst-theme.css`, this project's own
stylesheet from `myst.yml`'s `style:`, which the theme loads through its own `links()`
export and therefore re-adds itself. One rule per distinct size — 109 of them for 193
figures — keyed on the fingerprinted filename, saying `width` and `aspect-ratio`, which is
what the two attributes do between them.

Measured on a hydrated page, with an image that never loads: **with its rule it reserves
284×274, without one it reserves 722×28.** The second number is the layout shift this site
has today, and the first is the fix.

The block sits in `@layer figure-dimensions`, which is what keeps it from winning arguments
it should lose. An unlayered declaration beats a layered one whatever the specificity, so
every rule the theme writes still takes precedence — including `[&_img]:w-full img`, the

§18 recorded that this theme "does not hydrate, it re-renders", that every page logs React

### Getting the two arguments out of a production build

React's #418 page names two arguments and the minified URL shows
`?args[]=HTML&args[]=` — the first says "HTML" rather than "text", the second is empty
because production computes the diff string as the literal `""`. There is no non-minified
build to switch to and no amount of reading the URL will say more.

What does say more is the fiber. In the bundle, `throwOnHydrationMismatch` minifies to

```js

```

and three module-scope variables in the same closure are declared together right above it
(`var vl=null,J=null,q=!1,Xt=null,Vl=!1,tc=Error(b(519))` — React's
`hydrationParentFiber, nextHydratableInstance, isHydrating, hydrationErrors,
rootOrSingletonContext, HydrationMismatchException`). 745 bytes inserted before the throw

change to the chunk — the same pattern as `tools/thebe_gate.py`, for the same reason. It
is a scratch probe on a gitignored artifact, not a tool, and nothing in `tools/` changed.

DOM fibers carry their tag name as a plain string even minified, so that is enough. On the
deployed pipeline it says:

```
wanted: fiber tag 5 (HostComponent), type "link", rendered by Remix's <Links>
into:   fiber tag 27 (HostSingleton), <head>
found:  <link rel="stylesheet" href="/vendor/katex/katex.min.css">
```

### Cause 1, on all thirty pages: `vendor_assets.py` leaves the JS disagreeing with the HTML

React 19.2.7's `canHydrateInstance` — minified `Lh` — compares, for a `<link>` it does not
manage itself, **exactly four attributes**:

```js
case"link": if(e=l.getAttribute("rel"),e==="stylesheet"&&l.hasAttribute("data-precedence"))break;
  if(e!==n.rel||l.getAttribute("href")!==(…n.href…)||l.getAttribute("crossorigin")!==(…n.crossOrigin…)
    ||l.getAttribute("title")!==(…n.title…))break;
  return l;
```

The theme declares KaTeX in `build/_shared/chunk-WGW5MSUV.js` as

```js
{rel:"stylesheet",href:"…/katex.min.css",integrity:"sha384-MlJdn/…",crossOrigin:"anonymous"}
```

`vendor_assets.py` rewrites the href in the HTML **and** in the JS, and strips `integrity`
and `crossorigin` from the HTML `<link>` — deliberately, and the argument in its docstring
is a good one. It does not strip them from the JS. So the document says `crossorigin` is
absent and the props say `"anonymous"`, the link does not match, and because `<head>` is a
HostSingleton React scans forward through the remaining children rather than failing at
once, finds no other `<link>` that matches, and throws.

Why a stylesheet link is matched by position and attributes at all, rather than hoisted:
`isHostHoistableType` (minified `u2`) treats `rel="stylesheet"` as hoistable only when
`precedence` is a string, and Remix's `<Links>` passes none; and the hoistable lookup map
(`T1`) explicitly excludes `link[rel=stylesheet]` from the nodes it will claim. Hence
fiber tag 5, which is what the probe reported.

### Cause 2, on the twelve Markdown pages: `head_meta.py` section 5

Section 5 drops `thebe-core-<hash>.css` and `/vendor/jupyter-matplotlib/mpl_widget.css`
from the pages with no `myst-jp` marker. Its docstring already knew the client re-adds
both, because Remix's `links()` is one static array for all thirty pages. What it did not
know is the price: the client does not *re-add* them, it fails to find them. React wants
its second stylesheet link, the document's second stylesheet link is font-awesome, and
that is the second `found` the probe reports.

**Isolated.** With cause 1 fixed and nothing else: the eighteen notebook pages hydrate
(six stylesheets, no duplicates, canonical and `og:url` present), and the twelve Markdown
pages still throw — `continuous-distributions`, `covariance`, `data-protection`,
`descriptive-statistics`, `expectation-variance`, `intro-stochastics`,
`random-variables-distributions`, `relative-entropy`, `statistical-models`,
`statistical-tests`, `what-is-data-science` **and the landing page**. Exactly the partition
section 5 acts on. With both fixed, 30 of 30.

### Why the symptom list looked like a theme that re-renders on purpose

When hydration of the document fails, React clears it with `clearContainerSparingly`
(minified `Uc`), which walks `<html>`, `<head>` and `<body>` and removes every child
**except** `SCRIPT`, `STYLE` and `LINK` whose `rel` is `stylesheet`. That one function is
the whole of §18's list: `<main>` goes, every injected `<meta>` and every `<link>` that is
not a stylesheet goes, the stylesheets stay and the fresh client render appends its own
copy of each — the duplication — and the JSON-LD block survives because it is a `SCRIPT`.
Measured in the broken state: `script[type=application/ld+json]` is 1, stylesheets are 10
with 4 duplicated, canonical and `og:url` and the font preloads are 0.

### The two fixes, both applied the same day

**Cause 1 — `vendor_assets.py`, no trade-off.** `strip_integrity()` already removes
`integrity=` and `crossorigin=` from the HTML tag; the JS form of the same two keys
(`integrity:"…"`, `crossOrigin:"anonymous"` inside the object literal next to the href it
already rewrites) has to go with them. That makes the bundle say what the docstring says
it decided, and it is the whole of the error on the eighteen notebook pages.

**Cause 2 — `head_meta.py` section 5, and it need not be given up.** The four attributes
`canHydrateInstance` compares do not include `media`. So instead of deleting the two
`<link>`s, set `media="not all"` on them: the tag is still there for React to match, the
stylesheet is still fetched off the critical path, and it never applies. Measured on
`/statistical-tests/` and `/covariance/` in the fixed build — no #418, the attribute
survives hydration (React does not patch it back), `document.styleSheets` lists both with
`media: not all`, and four stylesheets remain render-blocking instead of six. `media="print"`
behaves identically and was measured too; `not all` is the honest one, because there is
nothing on these pages for the rules to style in print either.

That fix leans on an attribute React's matcher happens not to compare, which is a thing to
write down rather than discover later: if upstream widens the comparison, these twelve
pages break the way they are broken today, and the fallback is to stop dropping the two
stylesheets at all. A guard belongs with it — section 5's own postcondition should assert
that the tags are present and inert, rather than absent.

Three notes for whoever writes it, two of them from the session that wrote section 5. The
partition stays as it is: `JUPYTER_MARKER = "myst-jp"`, zero on exactly the twelve Markdown
pages, and the docstring's argument for that marker over `jp-CodeCell` is unaffected by any
of this. The postcondition `no page with no jupyter output may still link a jupyter
stylesheet` is the line that fails first, and it should **change with the behaviour rather
than be deleted** — inverted to assert the tag is there and carries `media="not all"`, on
all thirty pages, checked against the file rather than against the run's own edits. And
section 5's prose has to be rewritten rather than trimmed: its claim was that the two
stylesheets leave the critical path and the client re-adds them, and the second half of that
was never true. If the fallback is taken instead and they are not dropped at all, the 87 kB
was never bought in the first place, and the docstring should say so plainly.

### Addendum, same day: fixing #418 does not fix the CLS, and that is now measured

Two sibling sessions arrived at the in-article table-of-contents `<nav>` as the CLS cause
while this was being written, and asked whether the probe contradicted it. It does not —
it separates the two, which is worth having in writing because §19 had left the re-render
as the leading suspect for the shift itself.

The `<nav>` is served **empty** — `<nav></nav>`, with `myst-outline` appearing nowhere in
the served markup — on the theme-only build *and* on the fully post-processed one. So it
is not a hydration mismatch: the theme renders nothing there on the server and fills it
after mount, which is why the clean build hydrates without complaint and still ends up
with a 312 px block where the document had none.

Measured at 375×812 with a buffered `layout-shift` observer, landing page:

| build | #418 | shift | at | shifted nodes |
|---|---|---|---|---|
| theme only, no post-processing | none | **0.168428** | 630 ms | `P`, `H2` |
| full pipeline, both fixes of §20 | none | **0.167966** | 2215 ms | `P`, `H2` |

One shift per load, no second entry, `hadRecentInput` false. The same magnitude on a build
that never re-renders as on one that does not either — and the same family as PSI's
0.1527. The shifted node is the intro paragraph, which is what Lighthouse names; the
`<nav>` above it is 312 px with two children in both builds.

**So three things follow.** The shift is the theme's, it is not #418, and **the §20 fixes
will not move CLS** — their return is the table above them, not this number. The timestamps
say the same thing from the other side: 630 ms and 2215 ms, both long after the 186 ms at
which the broken build discards the document. (Absolute timings here are from a
backgrounded browser pane and are not comparable between the two rows; what is comparable
is that both are post-hydration, and that the shift exists at all on the clean build.)

That also explains the null result from an unthrottled live load: slow the main thread —
a hidden pane here, 4× CPU throttling at PSI — and first paint lands before the fill, so
the fill becomes a shift. Fast, and it does not. A paint-ordering race, not a network one,
which is consistent with a score that is bit-identical across three builds.

Reserving the space is therefore a separate fix from this section's two, it is needed
whether or not they land, and it is the siblings' to make. The one number from here that
may help: 312 px on the landing page at 375×812, in its initial collapsed state.

#### And the insertion caught in the act: +340 px, one mutation, no timestamp needed

The sibling session asked for the one thing black-box measurement cannot reach — whether
the shift coincides with the `<nav>` being populated. A `PerformanceObserver` is the wrong
instrument for it here, because a backgrounded browser pane composites at about 1 Hz and
stamps the shift at the next frame it gets round to, a second or so late. The geometry does
not care about frames.

So: an inline `<script>` at the top of `<head>` — before the module scripts, therefore
before hydration — registering a `MutationObserver` over the whole document that samples
`main article > p`'s document-relative top on every `childList` record and keeps only the
records where it **moved**, with whatever was added that time. At 375×812, landing page:

| build | t | added | `nav.myst-outline` | first `<p>` top | Δ |
|---|---|---|---|---|---|
| theme only, no #418 | 42 ms | *(parse complete)* | absent | 444 px | — |
| | **1064 ms** | `DIV.myst-outline-section` | **312 px** | **784 px** | **+340** |
| full pipeline, both fixes | 51 ms | *(parse complete)* | absent | 444 px | — |
| | **274 ms** | `DIV.myst-outline-section` | **312 px** | **784 px** | **+340** |

**One move per load, in both builds, and it is that one.** Nothing else in the whole load
shifts that paragraph — not the fonts, not a figure, not the re-render. A single
`DIV.myst-outline-section` goes into the server-rendered empty container and everything
below it drops 340 px.

That closes it arithmetically too. 340 px in an 812 px viewport is a distance fraction of
0.4187; against the measured 0.168428 that puts the impact fraction at 0.402, and
0.4187 × 0.402 = 0.1684. The sibling session predicted 0.419 from production geometry
without having seen this. The 340 px is also their number to the pixel.

The layout-shift entries landed at 2089 ms and 682 ms against insertions at 1064 ms and
274 ms — in both cases the next composite of a throttled pane, which is why the timestamp
was never going to be the discriminator and the geometry was.

So the mechanism is settled and it is not this section's: the container is server-rendered
and its contents are not, the theme fills it after mount, and under any throttling that
puts first paint before the fill it is a shift. Reserving its height at build time is
reachable from `tools/` — a `min-height` on that container below the `lg` breakpoint,
computed per page — and that is the siblings' fix, not this one's.

## 22. `Content-Signal` is gone, and the line was in the wrong place anyway (2026-10-19)

Bing's robots.txt tester answers **"Syntax not understood"** for the
`Content-Signal: search=yes, ai-train=yes, ai-input=yes` added in §4.3 of the audit
(`c8c48bc`). Konrad reported it, and chasing it produced one real finding, one failed fix
and one decision.

### The finding: it was outside the group it was meant to scope to

`Content-Signal` is scoped to a user-agent group, exactly as `Allow` and `Disallow` are —
that is how it is specified and how Cloudflare's own managed file writes it. Ours was
appended to the end of the file, behind a blank line:

```
User-agent: *
Allow: /
Sitemap: https://datascience.konradvoelkel.com/sitemap.xml
                       ← a blank line ends the group (RFC 9309)
# Licensed CC BY-SA 4.0: …
Content-Signal: search=yes, ai-train=yes, ai-input=yes
```

So from `c8c48bc` until today the line belonged to no user agent at all. Anything that
*did* implement Content-Signal had nothing to attach it to.

### The fix that did not fix it

Moving it inside the group — directly after `User-agent: *`, before `Allow`, comments
inside the group too, since comments are line-level and do not break a group while a blank
line does — produced **the same Bing error**, tested by Konrad on the corrected file. Which
is what should have been expected: the directive is a 2025 extension Bing does not
implement, so a tester that reports unknown fields reports this one wherever it sits.

### The decision: drop the directive, keep the comments

Two reasons, and the second decides it.

The first is that we cannot tell from outside what Bing actually does with the line.
RFC 9309 §2.2 requires a parser to ignore what it does not recognise, and Bing's own
parser is not documented on this point. An unverifiable line **inside** the group that
carries `Allow: /` is a worse bargain than the same line outside it — so the correct
placement, which is the one the spec asks for, is also the one that puts the doubt where
it matters. That is an argument for not having the line at all rather than for putting it
back where it was.

The second is that the signal said nothing. `Content-Signal` exists to express *refusal* —
Cloudflare's default is `ai-train=no`. Ours said yes three times, which is exactly what a
consumer assumes in the absence of any signal. It restated, in a syntax nobody implements,
a permission that CC BY-SA already grants, and that this site already states in the HTML,
the JSON-LD, `llms.txt` and the three comment lines that remain directly below it.

So `robots.txt` now ends with the licence comments and no directive. Comments are safe
where the directive was not: every parser strips them, and they carry the same sentence to
whoever goes looking.

### The gate

The artifact gate now rejects **any** non-standard directive in `robots.txt` — anything
whose field is not `User-agent`, `Allow`, `Disallow`, `Sitemap` or `Crawl-delay` — and
requires both the licence comment and a `Sitemap:` line to still be there. Checked red on
a file with `Content-Signal` put back and on a file with the licence comment removed,
before it was kept. The rule is not "never add a directive"; it is that adding one is a
decision to be made against a crawler rather than in a text editor, and the error message
says so.

**What was given up:** a machine-readable *permission*, which for an open textbook is a
thing worth stating. If a successor to Content-Signal is ever honoured by a crawler that
matters — and the IETF AI Preferences work is where to look — this is the file to put it
in, and the gate is the line to change.

observed paint behind it is 1.4 s. The two answer different questions, and the audit has
been reading the second as if it were the first since §17.

### Why the flag moved FCP and not LCP, in one line of the data

Lighthouse publishes, per audit, what it estimates removing that thing would save. Across
all five slow runs:

| audit | LCP saving | FCP saving |
|---|---|---|
| `unused-javascript` (the theme's 1,040 KiB client bundle) | 5,100–5,250 ms | **0 ms** |
| `cache-insight` (GitHub Pages' `max-age=600`) | 7,200–8,250 ms | 150–750 ms |
| `render-blocking-insight` (four stylesheets, 47 KB) | 600 ms home, 1,400–1,550 ms chapters | **identical to LCP** |
| `unused-css-rules` | 150–300 ms | 150 ms |

`unused-javascript`: **5.1 s of LCP, zero of FCP.** The module bytes are absent from
Lantern's FCP graph and dominate its LCP graph. That is the whole mechanism §24 went
looking for. A `<link rel="modulepreload">` changes a resource's *priority*; Lantern's LCP
estimate is driven by the *volume* on the path. So dropping nineteen hints could move FCP
— and did, 3.5 s — and could not move LCP, and did not. Nothing about this was a surprise
to the model; it was only unattributed.

`render-blocking-insight` is the one row where the LCP and FCP savings are the same
number, on every run. It is the only part of LCP that behaves like a paint.

### What is reachable, and the answer is: almost none of it

The dominant subpart is element render delay. Inside it, by Lighthouse's own
what-if runs:

* **5.1–5.25 s — the theme's client bundle.** `chunk-WGW5MSUV.js` (471 of 619 KiB
  unused), `chunk-7FWBVTMU.js` (333 of 339), `chunk-LS4ALTVG.js` (217 of 265).
  `mystmd`'s `book-theme` output. Not reachable: this repository can change when those

* **7.2–8.25 s — `cache-insight`.** GitHub Pages fixes `max-age=600` and offers no header

* **600 ms (home) / 1,400–1,550 ms (chapters) — four render-blocking stylesheets.**
  `app-XNK7MHNS.css` (24 KB), `myst-theme.css` (10 KB), `font-awesome.css` (8 KB),
  `katex.min.css` (4 KB). All four are build output, none is a file in this repository.
  Three are structural — deferring the theme's own Tailwind build or `myst-theme.css`

**Nothing was patched.** The dominant subpart is not reachable from here, the reachable

`unused-css-rules` is also not what STATUS.md claims. Coverage names `app-XNK7MHNS.css`

### What this says about `--drop-modulepreload`

§24 deferred the keep / per-page / revert decision explicitly, *"because option 2
optimises a number whose largest component has never been attributed"*. It is attributed
now, and it removes option 2 from the table:

**Option 2 (per page) is void as an LCP measure.** It was proposed to drop the hints only
where a page has no code, keeping the landing page's win and handing the chapters their
TBT back. But no page's LCP responds to a hint, on any page, because the hints change
priority and the LCP model reads volume. There is no per-page LCP to win. What is left of
option 2 is a pure TBT trade, which this round did not measure and which §24 already
priced.

**Option 1 (keep) is what the data supports.** The LCP element is server-rendered text
that paints at the first contentful paint — measured, 6/6, exactly. So the 3.5 s §24
measured off FCP is 3.5 s off the moment a reader sees the title, which is 3.5 s off the
reader's LCP, whatever Lantern reports. The score does not register it because the score's
LCP is a byte-volume model of a page that has no LCP image. Reverting would buy back a
synthetic number by making every reader wait 3.5 s longer for the title. That is the
clearest form the trade has taken yet, and it says keep.

*(This is an inference, and marked as one: the observed LCP = FCP identity is from the r9
runs, which are all post-flag. It holds structurally — the `<h1>` is in the served HTML,
above the fold, with no resource of its own to wait for — but no observed pre-flag trace
exists to confirm it, and none can be had now.)*

**Decided, 2026-10-23: keep it.** Konrad took option 1 on the attribution above. The flag
in `pages.yml` stays as `ef910d0` shipped it, on all thirty pages, and the question §24
opened is closed. What the site now carries is a deliberate trade: 3.5 s earlier text for
every reader on every page, against 320–730 ms of TBT on chapters and six points of a
synthetic chapter score. The score is the thing being given up, knowingly, and this is the
line to point at the next time the number invites someone to revert it.

### Two things about measuring this site, for the next round

**PSI caches, and that is where §24's duplicate pairs came from.** The first attempt at

## 26. The cover is in the graph, and `thumbnailUrl` is not (2026-10-26)

§21 named the failure and §21 named the fix in one sentence: *"with no card of his own on a
page, the slot does not stay empty — it gets filled with somebody else's work, under his
name."* The slot there was `og:image` on two sibling sites. There is a second slot, on this
site, and until today it was filled with the wrong *shape* rather than with nothing:
`Book.image` on the landing page was `images/social-card.png`, 1200 × 630, landscape. That
is the correct image for a Twitter or LinkedIn preview and it is not a book cover, and
`Book.image` is where an answer engine deciding whether a thing is a book goes looking for
one.

`tools/cover.py` and `images/cover.png` — 1000 × 1500, portrait 2:3, the site's own
open-book mark with a wireframe globe in place of the 421 kB shaded one — were written in a
pass of their own earlier today and landed as `77e23ba`. Nothing in the build or the markup
referenced them: a cover that only exists in `images/` is a cover no parser can find. This
section is the wiring, and the three decisions it needed.

### What changed, in six files

| File | Change |
|---|---|
| `tools/structured-data.json` | `image` is now an `ImageObject`: `@id` `.../#cover`, `url` and `contentUrl` `.../images/cover.png`, `width` 1000, `height` 1500, `encodingFormat`, `caption`, `license` |
| `tools/inject_jsonld.py` | stops writing the card into `image`; checks instead that the file the node claims is in the build, and that it is portrait |
| `tools/llms_txt.py` | one line in the header naming the cover URL, its size and its licence |
| `.github/workflows/pages.yml` | copies `images/cover.png` to `/images/cover.png`; the artifact gate asserts the claim against the bytes |
| `.github/workflows/checks.yml` | `cover.py --check` and `--verify` beside the card's and the logo's |
| `tools/optimize_images.py` | `cover.png` joins `social-card.png` in `GENERATED` |

### `image`: the cover replaces the card rather than joining it

A node may carry several `image` values, and the tempting shape was both — cover first, card
second, each with its dimensions, and let the consumer pick by aspect ratio. It is one value,
the cover, for a reason that is about consumers rather than about schema: nearly everything
that reads `image` reads the first value, or any value, and offering a landscape banner at all
leaves the §21 failure available at a lower probability. There is nothing to trade away by
removing it. **The card is not demoted; it is unmoved.** `og:image` and `twitter:image` are
where every social preview actually reads, `head_meta.py` still pins them to the card on all
thirty pages, and nothing in this change touches them — measured on the local build below.

One nice consequence. The card has to be *discovered* at build time, because MyST fingerprints
asset filenames and the hash changes whenever `social_card.py` is re-run; that is why
`inject_jsonld.py` read it back out of `og:image`. The cover is copied verbatim to a path that
does not move, so its URL is a constant in the template and stable enough to be an `@id`. The
`og:image` read stays, demoted to what it always also was: the proof that `head_meta.py` and
the origin rewrite have both run on the landing page.

### `thumbnailUrl`: measured, and no

Not set, and this is the one of the three decisions that is settled by documentation rather
than by judgement:

* **schema.org** (checked against `schemaorg-current-https.jsonld`, fetched 2026-10-26)
  defines `thumbnailUrl` as "A thumbnail image relevant to the Thing", on `CreativeWork`,
  with `rangeIncludes` **`URL` only**. It cannot carry `width` and `height`, so it cannot say
  the one thing that makes the cover useful — its shape.
* **Google's `Book` documentation** names neither `image` nor `thumbnailUrl` in its required
  or recommended properties, for the work or for the edition. Its book feature is a `DataFeed`
  of editions with `isbn`, `bookFormat` and `potentialAction` (a `ReadAction` or `BorrowAction`),
  which this book is not and is not going to become.
* There is exactly **one** cover raster. A `thumbnailUrl` today would be the same 1000 × 1500
  file under a second property: a second URL for a consumer to choose between, and no new
  information.

What would change it: a genuinely smaller raster. `tools/cover.py --png-width` already writes
one, so the day a `cover-small.png` is committed the property has something true to say and
goes in — with a second shape check in `checks.yml` beside the first.

### The chapters do not carry the cover

The argument for is real and was not dismissed: Google reads one document at a time, so an
engine citing `/relative-entropy/` sees a `Chapter` node with no portrait image anywhere in
it. The argument against is that a chapter is not the book.

It is decided by a line this repository had already drawn, one property up. A chapter's node
*does* restate `inLanguage`, `isAccessibleForFree` and `license` from the book — because those
are true of the chapter — and it *does not* restate the author's name, profiles or affiliation,
only the `@id`, because "the identity is shared, the properties are a fetch of the landing page
away" (`inject_jsonld.py`, "One book, twenty-nine chapters, one author"). The cover falls on
the second side of that line without ambiguity: it depicts the work, not the part, and the
part's route to the work is the `isPartOf` it already carries. Putting it on twenty-nine
`Chapter` nodes would assert twenty-nine times that this picture is a picture of that chapter —
the "thirty books" mistake one property down.

A chapter page is not imageless either. Its `og:image` is the card, which is the right shape
for a link preview of a chapter, which is what a chapter gets linked as.

### `og:image` stays; the landing page gains a line in `llms.txt`, not an `<img>`

`llms.txt` already had the "About the author" block §21 added, so the file written for models
to read is where the cover goes for the audience that cannot read JSON-LD:

> The cover is at `…/images/cover.png` — 1000 x 1500 and portrait, CC BY-SA 4.0 like the rest
> of the book, so it may be reproduced with attribution. The landscape image in each page's
> og:image is a link-preview card, not the cover.

The second sentence is there because the distinction is the whole point and a model that has
both URLs and no guidance will pick the wrong one half the time.

**A plain `<img>` in `landing-page.md` was considered and is Konrad's call, not a side
effect.** Two things stand in front of it, and neither is a stylistic objection:

* TRANSLATION.md §1. A new block in the English edition is allowed, but only as a declared
  English-only addition in `sync/additions/landing-page.md.json`, "kept rare: this is a
  translation, not a rewrite". It is the same rule that keeps the JSON-LD block itself out of
  `landing-page.md`. An `<img>` would need either its own block or a `{raw} html` directive,
  which is a block too.
* `head_meta.py`'s own guard. `social_card()` **exits the build** if the landing page's
  `og:image` is not the project thumbnail, with the message "the landing page has acquired a
  figure. Which image is the book's card is a decision; make it in `myst.yml`" — because MyST
  prefers a page's first figure over `project.thumbnail`. A figure on the landing page is
  therefore not an addition, it is a decision about the card, and the build says so.

So the structured data and `llms.txt` carry it, the reader's page is unchanged, and the one
route that would put a cover in front of a human on the landing page stays open and
undecided.

### The build: a path that does not move, and the PNG only

`pages.yml` copies `images/cover.png` to `_build/html/images/cover.png` and the template
hardcodes that URL. MyST copies only the images a page *references*, under a content hash, and
nothing references this one — it is not a figure in the book, it is a picture of the book. A
fingerprinted URL could not play the part anyway: the node gives the cover an `@id`, and an
identifier that changes on every regeneration is not one.

`images/cover.svg` is **not** published. Its title is set as `<text>` in Inter rather than as
outlines (`cover.py`, "Text is text, not outlines"), so a browser without Inter renders the
cover in whatever it falls back to. Publishing it would offer a broken cover beside a correct
one. It stays a source file, which is what it was written to be.

### Four gates, and all four were made to fail on purpose

Four new, and one that had to move:

1. `checks.yml` runs `cover.py --check` (byte-exact on the SVG, which is written as text, like
   `course_diagram.py`) **and** `--verify` (shape only on the PNG, which is rendered, like the
   card and the logo). The cover is the one artefact that is both cases at once.
2. `inject_jsonld.py` resolves the node's own `image.url` against the build directory and fails
   if the file is not there, and fails if the declared height is not greater than the declared
   width.
3. The `pages.yml` artifact gate makes the same two assertions on the page it is about to
   publish, and then the one neither a tool nor a validator can make: it reads the IHDR of the
   file at that URL and compares it to the numbers in the markup.
4. `grep` for the cover URL in `llms.txt`, so the line cannot quietly disappear the next time
   that header is edited.

`optimize_images.py` is the one that moved rather than being added. `cover.png` has to join
`social-card.png` in `GENERATED`, or `--check` goes red asking for a palette pass that the next
`cover.py --check` would then report as an out-of-date cover. The arithmetic is five times the
card's — 161 kB → 52 kB, a saving of 109 kB — and it is still an *easier* call than the card's
was, because of who pays: no page loads the cover, so it is fetched once by a crawler that went
looking for it, while the card is fetched by every link preview. If the 109 kB is ever wanted it
belongs inside `cover.py`'s render step, where the next regeneration keeps it.

  `BASE_URL: ""` for the domain root, the publish gate already refuses a build whose
  `index.html` has no `$BASE_URL/build/` asset paths, and `/myst-theme.css` answers 200 on
  the live site. The element is a closed `<dialog>` — `display:none` by the UA stylesheet —
  which an inline script removes once it can read `--has-styling` off the loaded
  stylesheet. It is MyST's alarm for a broken deploy and **must not be removed**.
* **`data-nosnippet` does not work on a `<dialog>`.** Google documents it on `span`, `div`
  and `section` only, and illustrates the point with an example commented `NOT VALID: not
  a span, div, or section`. Adding the attribute to `<dialog id="myst-no-css"` costs one
  `sed` and buys exactly nothing — and it is worse than nothing, because it *looks* like
  the problem is handled. That is the §17 failure mode: valid markup making a claim
  nothing checks.
* **The text reaches no file written for a crawler.** It is absent from `llms.txt`,
  `llms-full.txt` and all 30 Markdown twins; in the HTML it exists once, inside the closed
  dialog, and does not appear a second time in a hydration payload.

So the premise is unmeasured and the proposed fix is inert. **If** the text is ever
actually seen in a live SERP snippet, the fix that would work is a `<div data-nosnippet>`
wrapping the dialog's `<strong>` and `<p>` but *not* its `<script>` — the script resolves
`document.currentScript.parentNode` and calls `showModal()` on it, so it has to stay a
direct child. That is a rewrite anchored on the theme's markup, which by the standard
`tools/thebe_gate.py` sets needs a guard that fails the build when the shape moves. Not a
one-line insurance, and not worth it for a snippet nobody has seen.

### A title suffix on every chapter: **declined**, it is §9 asked again

The report wants `… — Data Science with Python (Konrad Völkel)` appended to each chapter's
`<title>`. That is not a new idea here: it is MyST's own default, `{page} - {project}`, and
it was **measured and removed on 2026-10-16** (§9, `9e655a6`). The suffix is 48 of the ~60
characters a SERP renders and **on 29 of 30 pages it was truncated away entirely** — paying
nothing, spending two thirds of the line, and inviting Google to rewrite the title instead
of showing it. `tools/head_meta.py` trims it, `pages.yml` fails the deploy if a page or a
payload could get it back, and the audit folder records it as deliberate
(`FULL-AUDIT-REPORT.md` line 237, `findings/onpage.md` line 13). The brand is not lost:
`og:site_name` and the structured data both say it, which is the other reason §9 added
`og:site_name`.

Whether mystmd could do it from config, since that was the open question: **there is no
title-suffix field.** The suffix is the theme's hardcoded `{page} - {project}`; the
configuration and frontmatter references document `title`, `subtitle` and `short_title`
and nothing that sets or extends the HTML `<title>`. `site.title` is the only lever, it was
already tested in §9, and it is rejected there for a reason that has not changed: it is one
string doing two jobs — the chapter suffix *and* the landing page's whole title — and the
two want different lengths. So the report's version could only be had by post-processing
the built HTML, i.e. by writing a second tool to undo what `head_meta.py` does and deleting
the guard that stops it. The landing page keeps the book's full title, as it did.
