# How this edition is published, and what was wrong with it

Written 2026-10-14, after an external critique of the web edition was passed on. Every
claim below was checked against the **live site**, the built HTML and the CI
configuration — not against the source, and not against the critique's own reasoning.

The German original received the same critique and worked through it the same day; its
assessment is `todo/seo-kritik-bewertung.md` in ds-skript. This file is the English
edition's counterpart, and exists mostly to record the three things that differ here.

---

## 1. What the critique got wrong

**Its headline finding — that chapter URLs return 404 to crawlers — is false.** Measured:

```
/ds-en/            200        /ds-en/kmeans    301 -> /ds-en/kmeans/   200
/ds-en/robots.txt  200        /ds-en/sitemap.xml                       200
```

`myst build --html` writes `kmeans/index.html`; there is no SPA fallback, the body is
server-rendered (193 kB of text with JavaScript disabled), and Googlebot follows a 301
without complaint. The recommended fix — "run `myst build --html`" — is what the workflow
already did.

The critique was right that something was wrong with the sitemap. It guessed the cause
instead of fetching the file.

## 2. What was actually broken, and is now fixed

### The sitemap pointed at `localhost`. All 30 entries.

```
sitemap.xml:  <loc>http://localhost:3000/kmeans</loc>      ... 30 entries
robots.txt:   Sitemap: http://localhost:3000/sitemap.xml
```

MyST fetches `robots.txt` and `sitemap.xml` from its own dev server during the static
build and writes that server's origin into them. MyST 1.10 has no setting for the real
origin — `BASE_URL` sets only the path. So the site handed crawlers a sitemap in which
every URL pointed nowhere, and a `robots.txt` naming a machine that does not exist.

### No `rel="canonical"`, anywhere

MyST emits none. It matters here because the same text is also published as a PDF, and
because this edition is about to change host.

### `og:image` was relative *and* 267 x 50

```
<meta property="og:image" content="/ds-en/build/dd46c6ec….png"/>
```

OpenGraph requires an absolute URL — Slack, LinkedIn, Mastodon and WhatsApp cannot
resolve a root-relative one, so the preview card stayed empty.

**Beyond that, and this is the part neither critique nor the German assessment caught:
that image, `dd46c6ec….png`, is the Creative Commons BY-SA button — 267 x 50 pixels.**
MyST has no site-wide preview image; it takes the first image of a page, and where a page
has none it reaches for the first image of the project, which here is the licence badge
at the foot of the landing page. So 16 of 30 pages advertised the CC button as their
preview card. At 267 x 50 it is below the 200 x 200 minimum Facebook and LinkedIn
enforce, so making the URL absolute would have produced a rejected or hairline card
rather than a preview. Two further pages derived an SVG, which no platform renders as a
card at all, and one a 400 x 144 figure.

*(Corrected 2026-10-15. The first version of this file, and the German assessment, both
called that image "the site logo". It is not: the logo is `logo-wide-….svg` and was never
the fallback. The fix is unaffected, but the mechanism is worth stating correctly — it is
"first image on the page", not "the logo", which is why small figures broke it too.)*

**The German edition has the same fallback and the same problem; its `og:image` is now
absolute but still the 267 x 50 licence badge.** Passed upstream in `UPSTREAM-NOTES.md`.

### The fix

All of it is post-processing in `.github/workflows/pages.yml`, after the build and before
the artifact upload: rewrite the origin into `sitemap.xml` and `robots.txt`, give every
`<loc>` the trailing slash that actually answers 200, make `og:image` absolute, and add a
`rel="canonical"` plus `twitter:card` to each of the 30 pages. Nothing in the build or the
content is touched.

Plus a real preview card: `images/social-card.png`, 1200 x 630, generated by
`tools/social_card.py` and committed. `myst.yml` declares it as the project `thumbnail`,
so pages with a figure of their own keep theirs and the rest inherit the card; the four
pages whose derived image was unusable (an SVG, the logo, or 400 x 144) name it
explicitly in their frontmatter.

The deploy job now refuses to publish if a `localhost` URL survived, if the page count
and the canonical count and the sitemap entry count disagree, if any `<loc>` still points
at a redirecting URL, or if any `og:image` is still relative. The guards are written as
`if … then fail; fi`, not `check && fail` — a trailing `&& fail` makes the step fail
exactly when the check passes.

Both steps were extracted from the YAML and run against a copy of a real build before
being committed: 30 pages, 30 canonicals, 30 sitemap entries, all absolute.

## 3. The origin, and the move of 2026-10-15

`SITE_ORIGIN` and `BASE_URL` are one `env:` block at the top of `pages.yml`. Since
2026-10-15 they read:

```yaml
env:
  SITE_ORIGIN: https://datascience.konradvoelkel.com
  BASE_URL: ""          # custom domain serves from the root, not from /ds-en
```

The German edition deliberately stays where it is for now — HHU GitLab, HHU domain
(Konrad, 2026-10-15). Only this edition moved.

### Why GitHub Pages with a custom domain, and not the VPS

The obvious alternative was to serve the book from Konrad's own Hetzner box, next to the
other sites. It was rejected for this move, for three reasons:

1. **It would have needed a server key in GitHub secrets**, which `PLAYBOOK.md` §3.9
   records as a decision already taken and rejected ("CI-driven deploy of app or site was
   considered and rejected: it would put the keystore or a server key into GitHub
   secrets", LA DECISION §37). This repository has no secrets at all today, and that is
   worth keeping.
2. **GitHub redirects the old URLs for free, and with a real 301.** A tree of
   `<meta http-equiv="refresh">` stubs — the usual suggestion — is a soft redirect and
   strictly worse.
3. **The control argument is satisfied by owning the name, not the metal.** The domain is
   Konrad's, at INWX, in `~/files/work/server/dns/`. If GitHub ever becomes the wrong
   host, it is one DNS record and two lines in this workflow — which is exactly the move
   just performed, and it is now a rehearsed operation rather than a hypothesis.

The VPS remains available later; nothing in the build or the post-processing is specific
to GitHub Pages. Only the upload step would change.

### What was verified before the cutover

Built with `BASE_URL=""` and the deploy steps run against the artifact:

* 30 pages, 30 canonicals on `https://datascience.konradvoelkel.com/<slug>/`, 30 sitemap
  entries, `robots.txt` naming the right sitemap, every `og:image` absolute;
* JSON-LD present once, `url` and `image` on the new origin;
* `CNAME` written from `SITE_ORIGIN`, so it cannot drift from the canonicals;
* the artifact served from a local root and opened in a browser: assets, stylesheet,
  sidebar navigation and a chapter page all load with no `/ds-en` prefix anywhere.

**`CAA` was checked and permits this.** `konradvoelkel.com` carries
`0 issue "letsencrypt.org"` at the apex, which subdomains inherit; GitHub Pages issues
through Let's Encrypt, so the certificate can be provisioned. Had that record named a
different CA, the certificate would simply never have appeared — with no error anywhere
in the build.

### What must still be checked after the cutover

DNS and the repository setting are not things this repository can do. Once they are in
place:

```bash
curl -sI https://datascience.konradvoelkel.com/kmeans/ | head -1
curl -sI https://konradvoelkel.github.io/ds-en/kmeans/ | head -1   # expect 301
curl -s  https://datascience.konradvoelkel.com/robots.txt
```

The second line is the one to watch. GitHub redirects a project site's old
`username.github.io/<repo>/…` URLs to the custom domain once it is set, but **whether it
preserves the path after the repository name is worth confirming rather than assuming**.
If it redirects to `datascience.konradvoelkel.com/ds-en/kmeans/` instead of
`/kmeans/`, the fallback is to publish a small tree of redirect stubs from a second
workflow — worse than a 301, but correct.

The social card deliberately carries `konradvoelkel.com`, the author's own domain, rather
than the site URL: a URL baked into a PNG goes stale silently.

Still open, and no longer blocked by the move: the `hreflang` pair with the German
edition. It needs the German side to point back, which means a change in ds-skript's own
`pages` job; a one-sided `hreflang` is ignored.

## 3b. Accessibility findings from the second critique (2026-10-15)

Three claims about the rendered DOM, all checked:

* **The licence badge had no `alt`.** True, and it was our own raw HTML in
  `landing-page.md`. Fixed: it now reads "Creative Commons Attribution-ShareAlike 4.0
  licence badge". The German original has the same markup and the same gap.
* **The navbar logo had no `alt`.** True. The book theme has a `logo_alt` option; set in
  `myst.yml`. All 30 pages now carry zero images without an `alt` attribute (checked
  across the whole build, not just the landing page, which is where the critique looked).
* **The course diagram renders as an empty `<figure></figure>`.** True. MyST emits the
  mermaid source into the page's JSON payload and renders it in the browser; the static
  HTML holds an empty figure with no caption. *This one we cannot fix from the source:*
  the `mermaid` directive rejects a `:caption:` option (tested — "unexpected option
  caption"), and wrapping it in a `figure` directive would add a block and break
  alignment with the German original. The information itself is not lost to a crawler —
  the paragraph above the diagram and the table of contents below it carry the same
  structure in prose. Recorded in `UPSTREAM-NOTES.md` as a MyST limitation that affects
  both editions.

## 4. What the critique proposed that was already done

Chapter titles and per-chapter `description`s were the critique's points 3 and 4. Both had
already been inherited from the original in `68ce8b1` — 30 distinct descriptions, and
titles like `k-means: clustering, implemented from scratch` or `Numpy: vectorisation and
arrays`. The original deliberately **reformulated** the critique's suggested titles rather
than adopting them, because a chapter title is also the printed heading in a 328-page PDF
and the critique's phrasings are search strings, not chapter names. Four titles are still
thin (`Expected value and variance`, `Expectation maximization and Gaussian mixture
models`, `The most important discrete distributions`, `Introduction to Python`). The
second critique raised them again; **Konrad's decision of 2026-10-15 is to leave them.**

## 4b. Structured data (added 2026-10-15)

The second critique's one genuinely new and correct point: there was no JSON-LD. There is
now, on the landing page only — `tools/structured-data.json`, inserted into the built HTML
by `tools/inject_jsonld.py` from the deploy workflow.

Three decisions worth recording, because they depart from what was proposed:

* **`Book` + `LearningResource`, not `Course`.** The proposal declared `"@type":
  ["Book","Course","LearningResource"]` with `"provider": Heinrich Heine University
  Düsseldorf` and a `hasCourseInstance`. That would assert that this edition is a course
  offered by the university, which it is not — it is a translated book, and as of
  2026-10-14 deliberately not addressed to that curriculum at all (§6). Structured data
  is a claim made to search engines; a false one is worse than a missing one. The
  author's *affiliation* is a separate claim and a true one, so it stays.
* **Not in `landing-page.md`.** The proposal put the block in the page source via a
  `{raw} html` directive. That would be an extra block and would break alignment with the
  German original on the next `sync.py align`. It goes into the built HTML instead.
* **The card URL is read back out of the page**, not hardcoded: MyST fingerprints asset
  filenames, so the hash changes whenever `tools/social_card.py` regenerates the card.

The deploy job fails if the landing page does not end up with exactly one parseable
JSON-LD block whose `url` is this build's own origin and whose `image` is absolute —
stale structured data after a move is worse than none.

Verified on 2026-10-15 in both configurations: at
`https://konradvoelkel.github.io/ds-en/` and, in the migration dry run, at
`https://datascience.konradvoelkel.com/`.

## 5. What was decided against, for now

**"Stochastics".** The critique is right that the word is a niche term in English where
*Stochastik* is standard in German, and this is the one point where the English edition
faces a question the original never had. Against changing it: `TERMINOLOGY.md` makes it
binding, and it is load-bearing — the book needs a name for the field containing both
probability theory and statistics, and the opening figure of `intro-stochastics.md` is
about exactly that containment. A possible middle path, not taken yet: the part titles
live only in `myst.yml` and are not block-aligned with anything, so they could say
"probability and statistics" while the running text keeps the term. The cost is that part
titles are also the printed part headings.

**The project title.** `Data Science Lecture Notes from Konrad Völkel` is the PDF's
`\title{}`, and the author already appears as the byline. The German original is simply
`Data Science Vorlesungsskript` — the author's name in the title is an addition of this
edition, translating nothing. Changing it is cheap and alignment-free; it has not been
done because it renames the book.

## 6. What *was* changed in the text

On Konrad's decision of 2026-10-14, the landing page no longer addresses the Düsseldorf
BSc: named courses of that curriculum, its module handbook, its master's programme and
its "three semesters" of prerequisites were generalised to what they mean. Eight blocks
were rewritten in place, so block alignment is untouched and the staleness check cannot
see the difference — which is precisely why the divergence is tabulated in
`sync/notes/landing-page.md.md`. The rule itself is in `TRANSLATION.md` §2; the note at
the foot of the landing page still says where the book comes from, because provenance is
not courseware.

## 7. The third critique (2026-10-15), and what came of it

Checked against the live site, as before. Three of its claims do not hold: it asks to
verify a `<meta http-equiv="refresh">` stub that does not exist (GitHub issues a real
301, path-preserving — verified); it prescribes Cloudflare Bot-Fight and Caddy
`handle_errors` settings for a site that runs on neither (`server: GitHub.com`, `via:
varnish`), and reads a `PERMISSION_DENIED` from its own tooling as a property of the site;
and it asks for `alt` attributes that were added the day before. It also proposes adding
notebook downloads, which 29 chapters already have — `/build/kmeans-….ipynb`, 1.66 MB,
served as `application/x-ipynb+json`.

What it got right, and what was done:

* **A custom 404.** GitHub was serving its own "Page not found · GitHub Pages" with no
  way back into the book. `_site/404.html` now ships with the site, self-contained: no
  stylesheet, no script, no image, because MyST fingerprints asset names and any
  reference would rot silently. Its links are absolute, because GitHub Pages serves it
  under paths of arbitrary depth.
* **The course diagram is a real image now.** `tools/course_diagram.py` draws
  `images/course-structure.svg` from the same structure the mermaid block described. The
  static HTML had an empty `<figure></figure>`; it now carries an `<img>`, an `alt`
  describing the seven parts in order, and a caption. Mermaid could not take a
  `:caption:` (tested), and pre-rendering it would have pulled headless Chromium into the
  build for one picture. The SVG follows the reader's light/dark setting.
* **`llms.txt`, `llms-full.txt`, and Markdown per chapter.** `tools/llms_txt.py` writes
  each chapter's source to `<slug>.md` and `<slug>/index.md`, adds
  `<link rel="alternate" type="text/markdown">` to every page, and builds both index files
  in reading order. Written as a tool rather than the inline shell that was suggested,
  which had three faults: chapter titles live in YAML frontmatter and not in a leading
  `# ` line, so its `grep` would have labelled every entry with a slug; the landing page's
  source is `landing-page.md` while its URL is the site root, which its loop did not
  handle; and it sed-ed a multi-kilobyte payload into `</head>`.
* **The PDF.** `pages.yml` now installs TeX and builds `myst build --pdf` *before* the
  HTML build — MyST attaches the finished export to the site and renders the download
  button from it, so the order is the whole trick. The step is allowed to fail: a book
  this size has many ways to upset latexmk, and a broken PDF must not take the website
  down. When it fails the deploy logs a warning instead of leaving it to be discovered by
  a student who wanted the download. 318 pages, 19 MB, built and checked locally first.

*Correction, same day.* The first CI build of the PDF produced an 84 kB stub: xelatex
cannot include an SVG, the runner had ImageMagick but nothing for it to delegate
rasterisation to, and latexmk's force mode reported success anyway. Fixed with
`librsvg2-bin`, plus a floor that deletes an implausibly small PDF before the HTML build
so no download button is attached to it. **The commit message for that fix guesses that
the German original has the same gap. It does not.** Its figures in those chapters are
PNGs with German labels; this edition redrew them as SVG in order to relabel them in
English, which is why only this edition needs an SVG converter. Checked:
`ds-skript/images/` contains exactly one SVG, the logo, and it is not in the PDF.

And one thing the critique could not have known to ask for: `tools/check_pdf_articles.py`,
ported from the original. `myst.yml` holds the book's structure twice — once as the toc,
once as the PDF's article list — and a chapter present in one but not the other is
invisible in the printed book with nothing to say so. The original was bitten by this
twice. Publishing a PDF without that guard would have imported the trap along with the
feature.

## 7b. hreflang (2026-10-15)

Both editions now link to each other, so the language pair could finally be declared.
This edition's half ships: three tags per page -- the German counterpart, a
self-reference, and `x-default` pointing at the English edition, which is the one that
serves readers whose language matches neither.

The pairing is not guessed. `sync/filemap.json` already maps every German source file to
its English counterpart; it is what the staleness tooling runs on and what CI checks, and
chapter-to-chapter hreflang is that mapping rendered as link tags. The slugs genuinely
differ -- `kovarianz` against `covariance` -- which is the case hreflang exists for. All
30 German targets were fetched once and answer 200.

`tools/hreflang.py` refuses rather than guesses: it will not run before the canonical
exists, it will not emit a self-reference that disagrees with the canonical, and it stops
if two English pages claim the same German counterpart. The deploy then counts three tags
per page and checks the German URLs are unique, because a cluster missing its
self-reference is discarded whole and a duplicated counterpart poisons both clusters.

**What CI here cannot check is the half that matters most.** A one-sided hreflang is
ignored, and the German side's tags live in ds-skript. `tools/hreflang.py --verify`
fetches the German pages and reports how many pairs are actually bidirectional; it is
deliberately not in CI, because it would make every deploy depend on a server that
GitHub's runners already cannot reach reliably. Run at the time of writing it says
`0/30`, which is correct: ds-skript has not landed its half yet. Publishing ours first
costs nothing -- an unmatched declaration is ignored, not penalised -- and the pair starts
counting the moment the other side appears.

## 7c. Figure descriptions (started 2026-10-16)

Every figure this book draws — 156 of them — offered `<Figure size 2000x2000 with 2 Axes>`
as its text alternative. That is worse than an empty `alt`: a check for "is alt missing?"
passes cleanly while a screen reader reads out nonsense and image search finds nothing.
All the accessibility work of 2026-10-15 (§3b) was about the handful of static images and
missed this entirely, because the figures are notebook *outputs*.

MyST takes an output image's `alt` from that output's own `text/plain`, and matplotlib
writes its repr there. The German original tried every other route first — cell metadata
in five spellings, `:alt:` on a `{figure}` directive wrapping a captioned code cell — and
this version of MyST ignores all of them. So the truth lives in `alt-texts.yml` and
`tools/alt_texts.py --apply` writes it into the notebooks. Re-executing a notebook undoes
it, which is why CI checks.

Set up and finished here on 2026-10-16. All 156 are written, and the result was measured
rather than assumed: across the 30 built pages there are 226 images, **none without an
`alt` and none still carrying the matplotlib placeholder**.

They are translations of the original's, which describe the same plots. That is defensible
because the random seeds are fixed: a figure pair was extracted from both editions and
differs only in the language of its title, the axes already being labelled in English on
both sides. The pairing is by cell id, and all 116 cells resolve.

Three differences from the original's version, all deliberate:

* **Two gates rather than one.** `--check` fails only on drift, which is what a
  part-finished chapter needs; `--complete` also fails on a figure without a description.
  CI runs `--complete` now that the work is done. The distinction earned its keep the same
  day: it let the descriptions land in six batches without a red build between them.
* **Empty counts as missing.** Upstream looks for the matplotlib repr; an output with no
  `text/plain` at all slips through that. Four animation cells are exactly that case —
  MyST does not render them as images, which is why the built pages come out clean — and
  they are listed in the tool by name and reason rather than passed over silently.
* **`--skeleton` emits stubs** for one notebook with the drawing code as context, because
  the writing is the work and finding the cells should not be.
* **The descriptions are written, not translated.** The plots are labelled in English and
  a description has to match the picture in front of the reader, not the German sentence
  about a German picture.

Four notebooks had to be normalised first: they were nbformat 4.4 with no cell ids, and
ids are what the descriptions are keyed to, because cells move and ids do not. The ids
were adopted from the original, whose cells correspond one to one — so a figure now
carries the same id in both editions, and the two books' descriptions can be held against
each other later.

## 8. The process failure behind all of this

The original fixed its sitemap, canonical and `og:image` on 2026-10-14 (`d929f14`,
`6e75f56`, `c3e74d3`). Every one of those fixes lived in `.gitlab-ci.yml`. `sync.py`
hashes blocks of mirrored content files, so the weekly upstream check reported nothing —
correctly — and this edition kept serving a sitemap full of `localhost` URLs.

The rule that follows is `TRANSLATION.md` §9: when the pin moves or a staleness issue
opens, also read the original's log for commits touching CI, `myst.yml` and `tools/`.

## 9. The fourth audit (2026-10-16), and what it cost to act on

Measured, not reasoned about: all 30 pages fetched from the live site, Core Web Vitals
taken in a real browser, every claim below checked against the artifact afterwards.

### What held

Everything the first three rounds built. 30/30 pages 200 and server-rendered; 30
canonicals, 30 sitemap entries, all absolute and all with the trailing slash that answers
200; `robots.txt` right; a real path-preserving 301 from `konradvoelkel.github.io/ds-en/`
(§3 left this one open — it is now confirmed); a 404 that returns 404; JSON-LD parsing
with the right origin; `lang`, viewport, one `<h1>` per page and **zero skipped heading
levels** across all 30; 226 images with no missing `alt` and no matplotlib placeholder;
mobile clean, with code blocks scrolling inside their own `overflow-auto` parents; CLS 0.

**And the hreflang pair is live: `tools/hreflang.py --verify` now says 30/30
bidirectional.** §7b recorded `0/30` because ds-skript had not landed its half. It has.
Nothing here had to change for that; the declaration published in advance simply started
counting.

### What was actually wrong

**The figures, which is where the whole budget went.** 197 distinct images, 21.3 MB. On
`descriptive-statistics` the measured LCP was **2712 ms against a 2500 ms budget** on a
fast desktop with a warm CDN, and the LCP element was `ds-process-oneill.png`: 3678×2259
and 5.79 MB, rendered at 480×295. Total transfer for that page, 7.99 MB over 43 requests.

Three separate causes, and the second is the one that mattered most:

1. *Oversized sources.* Five images served at more than twice their display size; one at
   1432×513 shown at 54×19.
2. *RGBA.* Matplotlib writes an alpha channel the plots do not use, and PNG compresses
   four channels far worse than one. One 790 kB figure has **232 distinct colours** — as a
   palette image that is not an approximation, it is the same bytes-for-pixels picture at
   a quarter of the size.
3. *Preload.* MyST emits `<link rel="preload" as="image">` for **every** figure on the
   page — twelve on kmeans. That, not the absence of `loading="lazy"`, is why a chapter
   fetched its whole figure set before the load event. Adding the attribute alone would
   have done nothing at all: a preloaded image is fetched regardless, and the preload
   wins. The two had to move together.

Result: `images/` 9.0 MB → 3.6 MB, the build's figures 9.0 MB lighter of 23.2 MB, and the
on-load image payload of `descriptive-statistics` 6.4 MB → 1.66 MB.

**Google Fonts, imported from our own stylesheet.** Line 3 of `_site/custom-style.css`.
Three costs, and the third is the embarrassing one: a three-deep render-blocking chain, a
third party on every page view, and the precise arrangement LG München I awarded damages
over in January 2022 — in a book with a GDPR chapter that cites noyb. Self-hosted now;
`_site/fonts/PROVENANCE.txt` has the files, hashes, licences and the reasoning, and the
deploy fails if a `https://fonts.googleapis.com` reference ever comes back.

**The title suffix.** `- Data Science Lecture Notes from Konrad Völkel` is 48 of the ~60
characters a SERP renders, and on **29 of 30 pages it was truncated away entirely** —
paying nothing, spending two thirds of the line, and inviting Google to rewrite the title
rather than show it. Chapters now carry their own title alone; the landing page keeps the
book's.

*Correction to the audit that prompted this.* It also said the suffix ate into four
chapter titles. It did not: those four are over 60 characters by themselves, and since
the chapter title comes first a suffix cannot push it out — only fail to fit after it.
Konrad's decision of 2026-10-15 to leave those four (§4) is untouched and unaffected.

**`og:url` and `og:site_name`, absent on all 30.** MyST writes `og:title`,
`og:description` and `og:image` and stops.

### The trap in doing it

Editing `<title>` in the markup fixed nothing a browser would see. The page is a Remix
app: the whole document is serialised a second time into `window.__remixContext`, and on
hydration the theme re-renders the title from *that*. The server-rendered head and the
hydrated head then disagree — and Google renders before it indexes, so the copy that
loses is the one we edited. Caught by loading the built page rather than grepping it.

`tools/head_meta.py` therefore blanks `project.title` in the payload too, for chapters
only, and `pages.yml` fails the deploy if a payload could put the suffix back. The logo,
the sidebar, the part names and the previous/next footer labels were all checked in a
browser afterwards: they come from their own fields and still render.

`site.title` in `myst.yml` was the obvious alternative and was tested — it does set the
HTML title independently of `project.title`, so it would not touch the PDF. It is not used
because it is a single string doing two jobs: it becomes the chapter suffix *and* the
landing page's entire title, and those want different lengths.

### What was deliberately not done

* **WebP.** Measured at 89% off a representative figure against 57% for palette PNG. Not
  taken, because the filename would have to change and the filename appears twice per
  page — in the `<img>` and inside the hydration payload. Get that half-right and the
  server-rendered page is fine while the hydrated one 404s every figure: invisible to a
  crawler, obvious to a reader. The half of the win that needs no reference rewriting
  went first.
* **The logo.** `images/logo-wide.svg` is 437 kB — one path alone is 117 kB of
  coordinates — and it loads on all 30 pages, which now makes it a quarter of
  `descriptive-statistics`'s on-load image payload. `svgo --precision 2` takes it to
  162 kB and looks identical to the eye, but 7% of pixels differ by a visible amount even
  at display size and svgo rewrites the `<text>` elements, so it is not a change to make
  silently to the book's logo. Precision 3 is clean (671 pixels of 180,000) at 32% off and
  still leaves 297 kB. **This wants a redraw or a raster export, not a squeeze**, and that
  is Konrad's call.
* **Blocking the PDF from the index.** See §9b.
* **The third-party CSS.** font-awesome 4.7, KaTeX and `mpl_widget` still come from cdnjs
  and jsdelivr on every page, render-blocking, with no `preconnect`. That is MyST's
  markup rather than ours, and unlike the font `@import` it is not ours to delete from a
  stylesheet; it needs either a theme override or a vendoring step of its own.
* **Per-chapter structured data.** Still only the landing page. `BreadcrumbList` and a
  `TechArticle` per chapter are defensible additions; they were not the day's bottleneck.

### 9b. The PDF, and what `Disallow` actually does

The audit's own phrasing — that `Disallow: /build/*.pdf` would keep the PDF "out of the
index while keeping the download working" — **is wrong, and worth correcting here rather
than quietly dropping.** `robots.txt` governs *crawling*, not *indexing*. A URL that is
disallowed but linked can still be indexed, as a bare URL with no description; Google
calls it "indexed, though blocked by robots.txt". And the site links the PDF from every
chapter's download button, so that is exactly the case that would arise.

The tool that actually prevents indexing is `X-Robots-Tag: noindex` in the HTTP response,
which requires crawling to be *allowed* so the header can be read. **GitHub Pages cannot
set response headers at all**, so that tool is not available here — a real cost of the
hosting decision in §3, alongside the 10-minute `max-age` on fingerprinted assets.

What `Disallow` would genuinely buy is narrower: Google could not read the PDF's contents,
so the PDF could not rank *for the text of the book* against the HTML chapters. What it
would cost is that the 19 MB download becomes invisible to anyone searching for a PDF of
the book, and that the URL may still surface, stripped of everything useful.

Not done, on that reading: a duplicate that cannot be described is a poor trade for a
download students actually use, and Google has handled PDF-beside-HTML for twenty years.
If it ever does start outranking the chapters, the lever is two lines appended to the
`robots.txt` rewrite in `pages.yml` — the file is already post-processed there — and it
can be added the day there is evidence for it.
